# 0037 — BI / Analytics & Dashboards: a **read-only `com.erp.modules.bi` aggregator** that composes the already-shipped query beans (owns **no business table**, posts nothing, computes on demand), a **role-aware operator dashboard** at `/admin/dashboard` (per-panel permission gating, four-state, drill-through), **company-wide AR/AP from the recon `subLedger` totals — never `ArAgeingQuery.ageing(companyId, null, …)`**, a **live 12-period revenue/net-profit trend** built by iterating `FiscalPeriodRepository` × `AccountMovementQuery.periodMovementByAccountType` (aggregate in SQL, never sum-in-Java), the **reporting export pipeline reused verbatim**, **chart-free v1** (stat-cards + CSS bars + tables), and a single additive **`V81__bi_permissions.sql`** seed (`BI.*` perms granted `ORG_ADMIN`)

- **Status:** Accepted
- **Date:** 2026-06-13
- **Deciders:** solutions-architect. Synthesised from three competing BI proposals (A lean-reuse, B rich-analytics, C dashboard-first) under three independent judge reviews. Judges 2 and 3 ranked **Proposal A the base** (the only design whose every reuse claim survives verification against the live code, and the only one that caught the `findOpenForStatement` `customerId` constraint that silently breaks B's and C's headline AR/AP ageing widgets); Judge 1 ranked **C the base** for its role-aware operator UX and the accurate `ModuleBoundaryTest` reading. The fused decision below takes **A's verified backend spine** (pure-composition service, company-wide AR/AP from the recon totals, iterate-periods trend, zero new table, one perm seed, export reused verbatim) and **grafts C's operator-grade frontend** (role-aware per-panel permission gating, graceful per-widget `forbidden`, first-class empty states, drill-through into existing detail screens, GL reads routed through `AccountMovementQuery` not a raw `JournalLineRepository` injection) and **B's honest top-N rule** (any true top-by-revenue lands as a GROUP-BY in the **owning** module's repo, consumed as a DTO — never faked over `journal_lines`).
- **Context source:** the Wave-2 codebase recon [docs/decisions/_wave2-recon/recon.md](_wave2-recon/recon.md), re-verified against the **shipped** code (latest migration **V80** `fx_revaluation_runs`, next free **V81**; next free ADR **0037**). Key live-code facts confirmed for this ADR:

## Context

The product has a rich, consistent set of on-demand read aggregates (the reporting engine, the AR/AP/cash/stock recon queries, the CRM pipeline KPIs, the dimension-sliced costing reads) but **no place that composes them into an at-a-glance executive view**. `/admin/home` is a static launcher with no numbers; every KPI surface today is a single-module screen (the CRM pipeline dashboard, the trial balance, the stock valuation report). The business wants one role-aware landing dashboard — a GM sees finance + cash + pipeline, an accountant sees AR/AP/TB health, an operations lead sees stock — with drill-through into the existing detail screens. The forces:

- **The lowest-risk shape in an ERP is a read-only aggregator that owns no state.** Reporting (ADR-0018) already proves it: a module that owns no business table, posts nothing, and computes on demand **cannot corrupt the ledger**. BI must take exactly that stance. Three proposals agreed on read-only; the decisive question was *how much new query surface BI adds*. A maps every widget 1:1 to a **shipped** bean and is **pure composition** (no `EntityManager`, no repository in `bi`); B and C add new repo methods, and one of B's additions (a chart-lib devDep) is a permanent build-surface cost. **A's pure-composition stance is chosen** because a BI service that holds no SQL **structurally cannot** re-query `journal_lines` or diverge from the financial statements — its numbers are the statements' numbers, by construction. Resolved in **D-1 / D-2 / D-3**.

- **The single most valuable correctness finding across all three proposals is the AR/AP ageing constraint — and it is grounded in live code.** B and C both specified company-wide ageing buckets via `ArAgeingQuery.ageing(companyId, null, asAt)` / `ApAgeingQuery.ageing(companyId, null, asAt)`. **Verified false:** `ArInvoiceRepository.findOpenForStatement` and `SupplierBillRepository.findOpenForStatement` hard-bind `AND i.customerId = :customerId` / `AND b.supplierId = :supplierId` with no null guard, so a null id returns an **empty list** — the ageing widget would silently render **zero receivables/payables**. A finance dashboard lying about AR is worse than omitting the widget. **A caught this and refused to fake it.** v1 sources company-wide AR/AP from `ArReconciliationQuery`/`ApReconciliationQuery` `subLedger` totals (genuinely company-wide, verified) for the stat-card + GL-tie health badge; a company-wide **bucketed** ageing widget is **deferred** (it needs exactly ONE new GROUP-BY in the owning repo — never a null `customerId`, never a Java loop over open invoices, NFR-REP-02). Resolved in **D-2 (W-AR/W-AP), D-10, Non-goals**.

- **C's `Top customers by outstanding` widget has no source as specified.** It claimed to reuse "`ArAgeingQuery` rows already keyed by customer." Verified false: `ArAgeingQuery.ageing` returns five `AgeingBucket`-keyed rows, never per-customer rows. Any true top-N (customers / products by revenue or outstanding) has no existing aggregate — `journal_lines` carries no customer/product dimension (only cost-centre/department/dimension3-4/project + project_id), and the AR repo has no `GROUP BY customer ORDER BY sum`. **B's rule is adopted:** if top-N is ever built, the GROUP-BY lands in the **owning** module's repo (`ArInvoiceRepository` / a sales-invoice-line repo), is exposed via that module's query bean, and BI consumes the DTO. v1 **defers top-N** and flags it to PM. Resolved in **D-10, OQ-BI-02**.

- **`ModuleBoundaryTest` does not forbid cross-module service injection — Proposal A overstated this.** Verified: the suite enforces controllers↛repositories, `@RestController` placement, services↛controllers, and audit-repo isolation only. BI injecting the shipped query beans and consuming their DTOs is **allowed today** and keeps the suite green, **so long as BI never imports another module's entity or repository**. So there is **no blocking ArchUnit precondition** and **no D-12 whitelist headline** — BI calls service beans + DTOs, routes its one GL read through `AccountMovementQuery` (not a raw `JournalLineRepository` inject, C's discipline), and we *log* "add a cross-module service-import ArchUnit rule" as future hardening, not a precondition. Resolved in **D-3**.

- **Time-series must aggregate in SQL and must not materialise a snapshot.** No `period_balances` table exists; all series are live (recon line 159). The trend is built by iterating `FiscalPeriodRepository.findByCompanyIdOrderByStartDateAsc` (≤12 periods) and calling `AccountMovementQuery.periodMovementByAccountType` per period — each call is one SQL `GROUP BY`; Java only **places** each result on the period axis, it never sums raw lines (NFR-REP-02). The escape hatch (if the ≤12 round-trips ever profile badly) is **one** `monthlyMovementByAccountType` GROUP-BY method added to `JournalLineRepository` (the sanctioned hub), consumed via `AccountMovementQuery` — deferred behind profiling, not built speculatively. Resolved in **D-4, OQ-BI-03**.

- **Day-1 and partial-permission users must get a calm, correct page.** A fresh company with no postings must show "No data yet for this period," not zeros that look like a bug; a user with only some BI perms must see the panels they hold and a calm `forbidden` panel for the rest — **never a whole-page 403** (the forbidden-redirect would bounce them to `/admin/home`). C's role-aware per-panel gating + first-class empty states deliver this and are grafted onto A's backend. Resolved in **D-6, D-7**.

- **Chart-free is the house style and the minimise-new-code mandate.** No chart lib exists; every KPI surface renders chart-free; WCAG 2.1 AA (PROJECT-CONVENTIONS §3.8) is CI-relevant and `<canvas>` charts carry a non-text-alternative burden. v1 ships stat-cards + CSS bars + tables with `[OK]`/`[!]` text-prefix health chips (a11y by construction). The DTO wire shape (arrays of `{label, value}`) is **chart-ready**, so a future `ng2-charts + chart.js` upgrade is a **template-only** v2 behind its own ADR. Adding the devDep in the BI base slice is rejected as scope creep. Resolved in **D-8, Non-goals**.

- **Schema freeze / direction.** BI owns **no business table**. The only migration is a permission seed, **`V81`** (latest shipped is V80), modelled on `V15__reporting_permissions.sql`: the `BI.*` perms granted `ORG_ADMIN`. `permissions.code` is free-form (`uq_permission_code` UNIQUE only — no module-enum CHECK to extend, verified). No new table ⇒ no `@Version` concern. Resolved in **D-5, Migration ordering**.

## Decision

### D-1 — A new **read-only** module `com.erp.modules.bi` that owns no business table, posts nothing, computes on demand (the reporting stance)

`com.erp.modules.bi` mirrors `com.erp.modules.reporting` (ADR-0018, BR-REP-08) exactly: it owns **no entity, no repository, no migration table**, writes **no outbox event**, and computes every figure on demand. Package shape:

```
com.erp.modules.bi
├── service
│   ├── DashboardService / DashboardServiceImpl   (@Service @Transactional(readOnly=true) — orchestrates ONLY)
│   └── BiExportFlattener                          (@Component — flatten(DashboardDto) → StatementRenderModel)
├── domain
│   ├── dto      (DashboardDto + the widget records + BiHeaderDto + HealthIndicatorDto — immutable records)
│   └── enums    (WidgetKind / HealthLabel as needed — no business enum)
└── (NO entity, NO repository, NO db/migration table)

com.erp.api
└── DashboardController   (@RequestMapping("/api/v1/bi") — thin; @PreAuthorize per endpoint)
```

`DashboardServiceImpl` is **pure composition** — it holds **no `EntityManager` and no repository** (the one exception, the read-only `FiscalPeriodRepository` for the period axis, is discussed in D-3/OQ-BI-01). It constructor-injects only the shipped query beans and `CompanyRepository` (for the header base currency), and composes their DTOs into `DashboardDto`. Because it holds no SQL of its own, it **structurally cannot** re-query `journal_lines` or produce a number the financial statements don't. Layering: `DashboardController → DashboardServiceImpl → (existing query beans)`.

`DashboardServiceImpl` injects and calls exactly these beans. Each widget DTO is an immutable record under `bi.domain.dto`; money is `BigDecimal` base currency; recon-backed widgets carry the source query's `ties`/`difference` flag surfaced as a health chip.

### D-3 — Cross-module boundary: BI calls **service beans + DTOs only**, GL reads route through `AccountMovementQuery`, never a raw repository or another module's entity

The boundary stance, stated **accurately** against the verified `ModuleBoundaryTest`:

- **Allowed today (suite stays green):** `bi.service` injects the shipped `@Component`/`@Service` query beans (`AccountMovementQuery`, `TrialBalanceQuery`, `ArReconciliationQuery`, `ApReconciliationQuery`, `StockValuationQuery`, `CashAccountStatementQuery`, `CashGlReconciliationQuery`, `PipelineQuery`) and `CompanyRepository` (for base currency) and consumes their DTOs. The four active ArchUnit rules (controllers↛repositories, `@RestController` placement, services↛controllers, audit-repo isolation) are **not** violated by this.
- **Forbidden (BI must never do this):** import another module's `..domain.entity..` or inject another module's `..repository..`. The single GL read BI needs (the trend) goes through `AccountMovementQuery` — **not** a fresh `JournalLineRepository` injection into `bi`.
- **The one repository edge (period axis):** the trend needs the fiscal-period spine `FiscalPeriodRepository.findByCompanyIdOrderByStartDateAsc`. **Default:** inject the read-only `FiscalPeriodRepository` (it is the documented time-series spine; it is a repository, not an entity, and ArchUnit does not forbid it). If the team prefers zero foreign-repo coupling from `bi`, expose that one read behind a thin gl/reporting **service** method — engineer's call at build time, recorded as **OQ-BI-01**.
- **Hardening (logged, NOT a precondition):** add a `ModuleBoundaryTest` rule that BI may depend on the enumerated query beans + their DTO packages but never on another module's entity. This is a *should-add* guard for the future, not a blocker for this slice — Proposal A's "ArchUnit whitelist headline" was an over-claim and is **rejected** as a precondition.

### D-4 — Time-series trend: iterate `FiscalPeriodRepository` × `AccountMovementQuery.periodMovementByAccountType` — aggregate in SQL, never sum in Java, no snapshot table

The ONE time-series widget (12-point monthly Revenue / Net-Profit) is built **live**, with zero new code in v1:

1. `FiscalPeriodRepository.findByCompanyIdOrderByStartDateAsc(companyId)` → the period spine; take the last N (default 12, `period_no` 1..12, `start_date`/`end_date`).
2. For each period call `AccountMovementQuery.periodMovementByAccountType(companyId, period.startDate, period.endDate)` (one SQL `GROUP BY` per call, `assertCanActIn`-guarded) and derive the period's revenue (INCOME net = credit−debit) and net profit (INCOME net − EXPENSE net, the `netIncomeForPeriod` convention).
3. Assemble `List<TrendPointDto>{ periodLabel, periodStart, periodEnd, value }` **server-side by bucket placement, never by summing raw lines** (NFR-REP-02 honoured — each total comes from a SQL aggregate; Java only places it on the axis).

This is ≤12 small GROUP-BY round-trips per dashboard load — acceptable for an executive dashboard (page-load only, cache-friendly). **Escape hatch (deferred behind profiling, v1.1 only):** add **one** `monthlyMovementByAccountType(companyId, fromDate, toDate)` GROUP-BY method to `JournalLineRepository` (the sanctioned hub: `GROUP BY a.accountType, date_trunc('month', e.postingDate)` in a single query), consumed via `AccountMovementQuery`, collapsing the 12 round-trips to 1. Confirm an index supporting the `date_trunc('month', posting_date)` grouping exists (leans on `ix_journal_entries_company_date`) before shipping it; if not, that is a future additive expression-index migration gated on the profiling result, never built speculatively. **OQ-BI-03.**

### D-5 — Scope/permission enforcement (defense in depth) + the new BI permissions + `V81` seed

**Three layers, identical to reporting:**
1. `@PreAuthorize("@perm.has('BI.VIEW')")` on the composite read; the finer `@perm.has('BI.FINANCE.VIEW')` / `BI.OPS.VIEW` / `BI.CRM.VIEW` on the per-panel endpoints; `@perm.has('BI.EXPORT')` on exports.
2. `DashboardServiceImpl` calls `scopeGuard.assertCanActIn(RequestContext.get(), companyId)` **FIRST** in every method, before any query-bean call (defense in depth — the reporting stance; covers the `WipReconQuery`-style gap should any unguarded bean ever be folded in).
3. Each underlying query bean **re-asserts** (`AccountMovementQuery`, `TrialBalanceQuery`, the Ageing/Recon/Pipeline/StockValuation beans all call `assertCanActIn` per method — verified).

`companyId` is **always** an explicit `@RequestParam`, never inferred from the principal (so root can target a company, with the independent `ROOT_BYPASS` audit firing inside the underlying beans' existing `REQUIRES_NEW` path). **Branch authorization:** `assertCanActIn` checks **company only**; `branchId` on the CRM widgets is an **analysis filter, not an auth boundary** — documented as such (no branch-level isolation claim in v1). `journal_lines.branch_id` is a nullable analysis tag and no GL aggregate filters on it, so the financial KPIs are company-wide regardless of `branchId`.

**Permission model (v1 = a small, role-aware family).** Two coarse perms gate the route and export; three fine perms gate the panels (C's graceful per-panel degrade). This is a deliberate middle ground between A's 2-perm minimalism and C's 5-perm family: the fine perms are cheap to seed and enable the role-aware UX (a GM grant ≠ an accountant grant) without inventing a new RBAC concept.

- `BI.VIEW` — open the dashboard (route gate + composite endpoint).
- `BI.FINANCE.VIEW` — finance + working-capital + trend panels.
- `BI.OPS.VIEW` — inventory panel.
- `BI.CRM.VIEW` — CRM panel.
- `BI.EXPORT` — export the dashboard to PDF/Excel/CSV.

### D-6 — DTO shapes (immutable records, base-currency money-as-strings, nullable panels for graceful degrade)

- `WorkingCapitalDto{ arOutstanding, arTies, arDifference, apOutstanding, apTies, apDifference }`.

- `CashPositionDto{ total, List<CashAccountBalanceDto> accounts, cashTies }`.

### D-8 — Charting: **chart-free v1** (stat-cards + CSS bars + tables); chart.js deferred to its own v2 ADR

**Decision: ship v1 chart-free; add NO charting dependency.** Forces, weighed: (a) no chart lib exists; the house style is uniformly chart-free; (b) a real devDep is a permanent build/bundle/CI surface + `<canvas>` a11y burden against the minimise-new-code mandate; (c) WCAG 2.1 AA is CI-relevant — CSS bars + data tables are natively accessible, canvas charts need explicit text alternatives. v1 = stat-cards + CSS-bar widgets (a `div` with `[style.width.%]` and the numeric value as text beside it) + tables for cash accounts and the 12-month trend + `[OK]`/`[!]` health chips. **Reversibility:** the `DashboardDto` wire shape (arrays of `{label, value}` points) is already chart-ready, so a future ADR that adds `ng2-charts + chart.js` (the lightest Angular-idiomatic fit) is a **template-only** swap with **no backend rework**. We do not pre-build for charts now.

### D-9 — Export: reuse the reporting pipeline **verbatim** — flatten `DashboardDto` → `StatementRenderModel` → `ReportExporter`; ZERO new PDF/XLSX/CSV code

`BiExportFlattener.flatten(DashboardDto) → reporting.export.StatementRenderModel`, then `reporting.export.ReportExporter.export(model, ExportFormat{PDF,XLSX,CSV}) → ExportResult{ byte[], contentType, filename }` → the three shipped renderers. `DashboardController.download(ExportResult)` sets `Content-Disposition`; `ApiResponseAdvice` passes `byte[]` through un-wrapped (downloads keep their own headers for free). Gate exports on `BI.EXPORT` (mirrors `REPORT.EXPORT`).

**Fit check (verified against `StatementRenderModel.Row`):** the dashboard KPIs all flatten cleanly — `SECTION_HEADER` per panel, `LINE` per metric, `SUBTOTAL`/`TOTAL` where natural, and `RECONCILIATION` rows for the AR/AP/Stock/Cash/TB health ties (`Row.reconciliation(label, difference, ties)` preserves the `[OK]`/`[!]` text prefix the renderers emit — a11y-safe). Pipeline value+weighted maps to `current`+`comparative`. **The 12-month trend is the one shape that does not fit two columns** — flatten it as **12 `LINE` rows** (one per month, value in `current`), the boring fit that needs **NO render-model extension**. **Decision: do NOT extend `StatementRenderModel`/`Row` for v1; do NOT write a thin BI-specific CSV** (the generic `CsvStatementRenderer` covers the 12-LINE flatten). The dashboard export is inherently bounded (fixed widget set); still apply the `LEDGER_EXPORT_MAX_ROWS = 10_000` cap as belt-and-braces on any list. Multi-column pivot export is its own future ADR.

### D-10 — Non-goals / no-scope-creep boundary (each deferred item is fenced with a named escape hatch)

The following are **explicitly out of v1** and each is a future ADR, not a half-built v1 feature:

- **Company-wide BUCKETED AR/AP ageing** — needs ONE new GROUP-BY in the owning repo (`ArInvoiceRepository`/`SupplierBillRepository`, `GROUP BY ageing-bucket WHERE companyId = :companyId`), exposed via the owning query bean, consumed by BI as a DTO. **Never** a null `customerId`/`supplierId`, **never** a Java loop over open invoices (NFR-REP-02). v1 ships AR/AP **totals** (D-2 W-AR/W-AP) only.
- **Top customers / top products (by revenue or outstanding)** — no shipped aggregate; `journal_lines` carries no customer/product dimension. If built, the GROUP-BY lands in the **owning** module's repo (`ArInvoiceRepository` for customers; a sales-invoice-line repo for products), exposed via that module's query bean; BI consumes the DTO. Flagged to PM. (**OQ-BI-02.**)
- **Branch-scoped GL KPIs** — `assertCanActIn` checks company only; no GL aggregate filters `branch_id` (a nullable analysis tag). Branch GL trends need new branch-predicated repo methods **and** a branch-authorization decision — its own ADR.
- **`WipReconQuery` / manufacturing WIP health** — excluded until the bean gains `assertCanActIn` or BI guards it explicitly.
- **Interactive charts** — chart-free v1; `ng2-charts + chart.js` is a v2 ADR (template-only swap, D-8).
- **Multi-column trend export (PDF/XLSX pivot)** — flattened as 12 LINE rows in v1; a true multi-column export extends `Row` under its own ADR.
- **Materialised / snapshot tables** — none; all series live (compute-on-demand is the reporting stance; caching is out of scope).
- **Re-querying `journal_lines` from `bi`** — forbidden; the BI service holds no `EntityManager`/repository; GL reads go through `AccountMovementQuery`.

## Consequences

**Positive**
- BI is the lowest-risk shape in an ERP: read-only, owns **no business table**, posts nothing, writes no outbox — it **cannot corrupt the ledger** (the reporting/BR-REP-08 stance, ADR-0018).
- Every v1 KPI maps 1:1 to a **shipped, already-tested, already-scope-guarded** query bean, and the BI service is **pure composition** (no `EntityManager`, no repository in `bi`) — so BI numbers **cannot diverge** from the financial statements (same `AccountMovementQuery`, same recon ties, same CRM pipeline) and BI **structurally cannot** re-query `journal_lines`.
- The verified AR/AP stance closes the latent **silent-empty-ageing bug** that B and C both shipped: company-wide AR/AP come from the genuinely-company-wide recon `subLedger` totals, never from `ArAgeingQuery.ageing(companyId, null, …)`.
- It honours every hard invariant rather than working around them: `assertCanActIn` first on every read (reinforced by the beans re-asserting), `companyId` always explicit, role-aware `@PreAuthorize` perms seeded additively to `ORG_ADMIN`, the export pipeline reused verbatim (zero new PDF/XLSX/CSV code), `ApiResponse.ok` envelope, four-state `@switch` + signals frontend, append-only routing/nav.
- Operator-grade UX: a role-aware dashboard where a GM sees finance + cash + pipeline and an accountant sees AR/AP/TB health, each panel independently permission-gated and four-state with graceful per-widget `forbidden` (never a whole-page 403), first-class empty states for fresh tenants, and drill-through into every existing detail screen.
- Chart-free + CSS bars deliver a genuine visual dashboard with **zero new devDeps** and native WCAG-AA accessibility; the wire shape is chart-ready so a future `ng2-charts` upgrade is template-only.
- Fully additive (one `V81` perm seed) and reversible (delete the five rows).

**Negative / costs**
- Up to 12 GROUP-BY round-trips per dashboard load for the trend (D-4). Acceptable for an executive page-load; the single `JournalLineRepository` monthly-bucket method is the named escape hatch behind profiling.
- The composite `/dashboard` fans out to ~7 query beans serially; each is an optimised SQL aggregate but they add up. Mitigated by the per-panel endpoints + independent signal trios (panels render as they arrive); the composite is the primary call, panels are the fallback. No caching in v1 (compute-on-demand is the stance).
- Several embedded sub-DTOs (e.g. `StockValuationReportDto`, `ForecastDto` fallback) carry a hardcoded `"TZS"`; BI resolves the **header** currency via `CompanyRepository.getBaseCurrency()` and accepts the embedded inconsistency in v1 — it does **not** patch the shipped beans from BI (post-Wave-1 the ledger is base TZS, so it is correct today). Noted for a future cleanup.
- The role-aware fine-perm family (5 perms) is more RBAC surface to seed/maintain than a 2-perm minimum; chosen as the deliberate cost of the operator-UX value.
- A new cross-module dependency (BI → 7 modules' query beans) is a loose contract: an upstream DTO change can break BI — covered by the Tranche-1 service tests and the *should-add* ArchUnit hardening rule.

**Neutral / deferred** — company-wide bucketed ageing, top customers/products, branch-scoped GL KPIs, manufacturing WIP health, interactive charts, multi-column trend export, materialised snapshots, caching — all fenced (D-10), each a future ADR with a named escape hatch, none precluded (each is additive).

## Alternatives considered

- **Lean-reuse, snapshot-only, 2-perm (Proposal A) — CHOSEN as the backend spine.** The only design whose every reuse claim survives verification against the live code, the only one that caught the `findOpenForStatement` `customerId` constraint (the silent-empty-ageing bug in B and C), and the lowest-risk shape (pure composition, zero new repo code, one perm seed). Grafted onto it: C's frontend and B's top-N rule. Its over-claims were corrected — the ArchUnit "whitelist headline" (no such blocking rule exists, D-3) and the 2-perm minimum (raised to a small role-aware family for the operator UX, D-5).
- **Rich-analytics with charts + top-N + monthly GROUP-BY (Proposal B) — partially grafted, mostly deferred.** Its honest top-N routing (GROUP-BY in the owning module, BI consumes the DTO) is adopted as the deferral rule (D-10). Its monthly-bucket `JournalLineRepository` method is adopted as the profiled trend escape hatch (D-4). **Rejected for the base slice:** (1) it shipped the same null-id ageing bug as C (its headline ageing distributions would render empty); (2) it opens three new-code/new-dep fronts in one slice (chart.js+ng2-charts devDep, a thin BI CSV for the trend matrix, top-N repo methods in two other modules) — materially more surface than a base should carry against the minimise-new-code mandate. The chart.js devDep is deferred to its own v2 ADR (D-8).
- **Dashboard-first, role-aware, 5-perm (Proposal C) — grafted as the frontend + UX spine.** Its role-aware per-panel permission gating, graceful per-widget `forbidden`, first-class empty states, drill-through into existing screens, sibling `/admin/dashboard` route, and the accurate `ModuleBoundaryTest` reading (service beans + DTOs allowed; GL read via `AccountMovementQuery`, not a raw `JournalLineRepository`) are all taken. **Rejected from C:** (1) the same null-id ageing widget (replaced by the recon-totals stance, D-2); (2) the fabricated "Top customers by outstanding from ageing rows" widget (`ArAgeingQuery` returns bucket-keyed rows, not customer-keyed — deferred per B's rule, D-10); (3) the full 5-perm `BI.FINANCE/OPS/CRM.VIEW` family is trimmed to a coarse `BI.VIEW`+`BI.EXPORT` plus the three panel perms (kept — they earn the role-aware UX, D-5).
- **Materialised KPI / snapshot table (period_balances)** — rejected: none exists, compute-on-demand is the proven reporting stance, and a snapshot would introduce a staleness/consistency burden BI's read-only composition avoids. Deferred behind a future caching ADR if page-load profiling ever demands it.
- **Folding KPIs into `/admin/home`** — rejected: home is the forbidden-redirect target and must stay permission-safe and data-independent; a gated KPI fetch there risks a 403-loop. The dashboard is a separate `BI.VIEW`-gated sibling route; home gains only a static card.
- **BI calling the existing `/api/v1` controllers over HTTP (instead of injecting service beans)** — rejected: heavier (serialisation + an internal network hop), and unnecessary since cross-module service-bean injection is allowed today (D-3). In-process composition is the boring, correct choice.

- **OQ-BI-03 — trend fan-out profiling:** do the ≤12 GROUP-BY round-trips show on the page-load budget for a large `journal_lines`? **Default: ship iterate-periods in v1; add the single `JournalLineRepository.monthlyMovementByAccountType` GROUP-BY only if profiling demands it** (and only with a confirmed supporting index, else a gated additive expression-index migration).
- **OQ-BI-04 — `role_permission` table/column names:** confirm the join-table name and columns against `V1__baseline.sql` before writing `V81` (the FX ADR uses `role_permission SELECT r.id, p.id`; verify it matches the live baseline). **Default: mirror `V15__reporting_permissions.sql` verbatim.**
- **OQ-BI-05 — fine-perm granularity:** are three panel perms (`BI.FINANCE/OPS/CRM.VIEW`) the right cut, or does the business want them collapsed to a single `BI.VIEW` for v1 and split later? **Default: ship the three** (cheap to seed, enables the role-aware UX); collapsing later is a perm-removal migration.
- **OQ-BI-06 — default period window:** the dashboard's default `from`/`to` when the caller omits them — current fiscal period, or current calendar month? **Default: current OPEN fiscal period** (consistent with the trend's period spine); confirm with the business.
