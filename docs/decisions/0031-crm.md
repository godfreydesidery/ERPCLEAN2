This ADR is the **technical data model + integration design** for the CRM module (ROADMAP area 12, PATH-TO-FULL-ERP §3.9 / Phase D — thin v1). It translates the proposed spec into: the new `com.erp.modules.crm` module, the five tables (`leads`, `opportunities`, `opportunity_lines`, `activities`, `pipeline_stages`), the lead / opportunity / activity lifecycle enums + service-guarded transitions + the deterministic OPEN/WON/LOST + stage model, the configurable per-company pipeline-stage seed, the convert seam into the shipped O2C services (synchronous, idempotent via a unique `source_opportunity_uid` back-link added additively to `quotations`/`sales_orders`), the pipeline/forecast read model, the API surface, the perms + ScopeGuard cases + Angular routes, the `V51`/`V52` migration ordering with **#12-safe seeds**, and the ArchUnit edges (no cycle). It is **concrete enough that the backend engineer writes the model + the qualify-promote call + the convert seam + the pipeline read without guessing a business rule.** It writes **no production code, no entities, no migration SQL** — that is the engineer's next step. **CRM posts NO GL, moves NO stock, opens NO AR, introduces NO gl_config key and NO CoA account** — it is the only greenfield module that touches no money.

## Context

ERPCLEAN2 has the whole Order-to-Cash spine (ADR-0021) but nothing in front of it: no lead, no opportunity, no pipeline, no place to log the calls/meetings that precede an order. CRM is a **thin pre-sales layer** that captures the prospect, works the deal through configurable stages, logs the touches, and — on a win — **converts** to a real quote/SO by calling the shipped O2C services. The forces:

- **The Parties boundary is load-bearing (BR-CRM-01/09, the #1 design risk).** A lead is **not** a customer — capturing every tyre-kicker as a `customers` row would pollute the master. So the lead holds its **own** contact details **in CRM** and only on **qualify** is a Parties customer **linked** (existing) or **promoted** (new, via `CustomerService.create`). CRM must add **no column or table to Parties** — no `contacts` table (deferred §2). The question is purely *where the lead's contact data lives* (CRM) and *how the customer is joined* (a nullable `customer_id` set on qualify). Resolved in **D-3**.

- **The convert seam is the one cross-module write (OQ-CRM-01/02, the load-bearing decision).** Converting an opportunity must produce a **real** quotation/sales order through the shipped `QuotationService.create` / `SalesOrderService.create` (+ `addLine` per opportunity line) — CRM does not reimplement quoting. Two questions: (1) **where the opportunity↔document link lives** — an additive `source_opportunity_uid` on the O2C `quotations`/`sales_orders` (lean, mirrors ADR-0021's `source_quotation_uid`) vs a CRM-side link table; (2) **sync vs event** — a synchronous service call (the user sees the quote immediately) vs an `OPPORTUNITY.WON` outbox event (decoupled, async). Resolved in **D-7**: synchronous call + the additive back-link column + a unique-constraint idempotency backstop.

- **Stage is a configurable per-company dimension; status is the lifecycle (BR-CRM-03/04).** An opportunity sits at one **pipeline stage** (a position in the open funnel, seeded + editable per company) and carries a separate **status** OPEN/WON/LOST (the close). These are **orthogonal axes** — the same modelling discipline ADR-0021 used for the SO's fulfilment/invoicing dimensions, but simpler (status is a stored enum; stage is an FK to a per-company master). Resolved in **D-2/D-4**.

- **CRM owns no financial effect (BR-CRM-05/10).** No GL post, no stock move, no AR item, no reversal mechanic. The only effect is the convert call into O2C. This makes CRM the simplest greenfield module: pure CRUD + pipeline + one outbound service call. The question is keeping the ArchUnit edges clean (`crm → sales.service`, `crm → parties.service`, no cycle). Resolved in **D-11**.

- **Schema freeze / direction.** IAM=V1 … Sales Returns=V19, all frozen. CRM is additive: **V51** creates the five CRM tables + the per-company pipeline-stage seed + the permissions + (lazy) numbering kinds; **V52** adds the one additive `source_opportunity_uid` column to `quotations` and `sales_orders` (the convert back-link) + its unique constraint. CRM imports no Sales/Parties *entity* — it reaches `parties.service` (qualify-promote) and `sales.service` (convert) the same way `sales.service` already reaches `stock.service`/`ar.service` (D-11).

## Decision

### D-1 — Module placement: a new `com.erp.modules.crm` module; controllers flat in `com.erp.api`; outbound edges to `parties.service` + `sales.service`

CRM is a **new sibling module** under **`com.erp.modules.crm`** (flat peer of `sales`/`parties`/`gl`, PROJECT-CONVENTIONS §2). It is **not** a sub-package of `sales` — CRM is pre-sales (leads/pipeline) with its own lifecycle and its own per-company stage master; it merely *feeds* sales on convert. A `sales.crm` sub-package would imply CRM is a channel of the invoice spine (it is not) and would muddy the `ModuleBoundaryTest` flat-peer reasoning. `crm` is the durable, boring name.

```
com.erp.modules.crm
├── domain.entity   Lead, Opportunity, OpportunityLine, Activity, PipelineStage
├── domain.dto      LeadDto / CreateLeadRequest / UpdateLeadRequest / QualifyLeadRequest,
│                   OpportunityDto / CreateOpportunityRequest / UpdateOpportunityRequest /
│                       AdvanceStageRequest / WinOpportunityRequest / LoseOpportunityRequest /
│                       ConvertOpportunityRequest / ConvertResultDto,
│                   OpportunityLineDto / AddOpportunityLineRequest,
│                   ActivityDto / CreateActivityRequest / CompleteTaskRequest,
│                   PipelineStageDto / CreatePipelineStageRequest / UpdatePipelineStageRequest /
│                       ReorderPipelineStagesRequest,
│                   PipelineSummaryDto / PipelineStageSummaryRowDto / ForecastDto / CrmKpiDto  (D-9)
├── domain.enums    LeadStatus, LeadSource, OpportunityStatus, ActivityType (D-2)
├── repository      LeadRepository, OpportunityRepository, OpportunityLineRepository,
│                   ActivityRepository, PipelineStageRepository
└── service         LeadService(+Impl), OpportunityService(+Impl), ActivityService(+Impl),
                    PipelineStageService(+Impl),
                    OpportunityConversionService(+Impl)   — the convert seam → O2C (D-7),
                    CrmNumberGenerator                    — LEAD/OPPORTUNITY/ACTIVITY via code_sequence (D-8),
                    PipelineQuery                         — pipeline/forecast/KPI read aggregate (D-9),
                    CrmStageSeeder                        — seeds default pipeline stages for a new company (D-4)
```

Controllers stay flat in `com.erp.api`: `LeadController`, `OpportunityController`, `ActivityController`, `PipelineStageController`, `PipelineController` (the read model). They touch only services (`ModuleBoundaryTest`). CRM has **no `events` package** — there is no CRM-owned domain event in v1 (the convert is synchronous; D-7).

**Boundary note (D-11):** CRM reads **DTOs only** from Parties/Sales/Products (never their entities/repositories). The cross-module references it persists are **scalar `Long` id + `String` uid columns** with real DB FKs *within the CRM tables only* (e.g. `customer_id` → `customers(id)`, `agent_id` → `agents(id)`, `app_user_id` → `app_users(id)` for owner/assignee) — these are FKs to frozen V1/V2 tables, the same scalar-FK-to-another-module stance ADR-0021 takes (`sales_order_lines.product_id` → `products(id)`). The qualify-promote effect calls `parties.service.CustomerService.create` (returns a DTO); the convert effect calls `sales.service.QuotationService`/`SalesOrderService` (returns DTOs). No cross-module `@ManyToOne` to a Parties/Sales *entity*.

### D-2 — Lifecycle + enums (the exact set, transitions, and the stage-vs-status split)

Four new enums in `crm.domain.enums`. Every transition is **service-guarded, audited, append-only** (NFR-CRM-04, BR-CRM-10); status/stage are **never free-set on a closed record** (BR-CRM-03/04).

**`LeadStatus`** (FR-CRM-01/02, BR-CRM-01/02):

```
NEW ──contact──▶ CONTACTED ──qualify──▶ QUALIFIED ──(opportunity created)──▶ CONVERTED   (terminal)
  │                  │                       │
  └──────────────────┴───────────────────────┴──disqualify──▶ DISQUALIFIED   (terminal; mandatory reason)
  (hard delete allowed while NEW — consumed no LEAD-#### until create; LEAD-#### at create — see D-8)
```

- `qualify` (FR-CRM-03) sets `customer_id` (link existing) or calls `CustomerService.create` then sets it (promote new) and moves to QUALIFIED. A lead **cannot** be QUALIFIED without a resolved `customer_id`.
- `CONVERTED` is set when an opportunity is created from the lead (FR-CRM-04); `DISQUALIFIED` requires a reason. Both terminal.

**`LeadSource`** (FR-CRM-01): `WEBSITE | REFERRAL | WALK_IN | CAMPAIGN | COLD_CALL | EXISTING_CUSTOMER | OTHER`. (Coarse origin; full campaign object deferred §2.)

**`OpportunityStatus`** (FR-CRM-05/06/07, BR-CRM-03/04) — the **lifecycle** axis (orthogonal to the stage):

```
OPEN ──win──▶ WON ──convert──▶ (stays WON; converted_document_uid set, D-7)
  │            │
  │            └──(WON may convert to QUOTE or SO)
  ├──convert(QUOTE only, OQ-CRM-04)──▶ (stays OPEN; quoting is part of negotiating)
  └──lose──▶ LOST   (terminal; mandatory loss_reason)
```

- **OPEN** — being worked; sits at one **pipeline stage** (the position axis, D-4); editable.
- **WON** — won (mandatory `won_at`); convertible to QUOTE or SO; immutable except activities + the convert stamp.
- **LOST** — lost (mandatory `loss_reason`); terminal; immutable except activities.
- **Stage vs status (the orthogonal-axes decision, BR-CRM-04):** the **pipeline stage** is an FK (`pipeline_stage_id`) to the per-company `pipeline_stages` master (D-4) — it is the *position in the open funnel* and is meaningful only while OPEN. The **status** is the stored `OpportunityStatus` enum — the *lifecycle close*. They never collapse into one column: an OPEN opportunity has a stage; a WON/LOST one keeps its last stage for reporting but the status is the headline. `CONVERTED` is **not** an OpportunityStatus value — conversion is recorded by `converted_document_uid` + `converted_document_kind` on a WON (or OPEN→quote) opportunity, not a status (a converted WON deal is still WON; the convert is an event on it). This keeps `status` a clean 3-value filterable enum.

**`ActivityType`** (FR-CRM-10/11): `CALL | EMAIL | MEETING | NOTE | TASK`. A `TASK` carries `due_date` + `assignee_id` + `done` (BOOLEAN); the other four are historical records (no due date). The done-flag is the only activity transition (open → done), audited.

**Seed per new company (BR-CRM-04, the `ApGlSeeder`/`CrmStageSeeder` pattern):** on company create (wired in `CompanyService.create` + `BootstrapRunner`, the shipped per-module seeder pattern), `CrmStageSeeder` inserts the default set: `QUALIFICATION 10 / NEEDS_ANALYSIS 25 / PROPOSAL 50 / NEGOTIATION 75 / CLOSING 90` (display_order 1..5). **#12-safe seed-uid:** the seeder runs **per company in Java** (not a CROSS-JOIN SQL seed), generating a fresh ULID per row — **no #12 exposure** (the #12 rule applies to per-company CROSS-JOIN SQL seeds; a Java seeder generating ULIDs is inherently safe). If a backfill SQL seed for *existing* companies is added in V51, it **must** use the #12-safe form `'CS' || lpad(company_id::text,6,'0') || substr(md5('QUALIFICATION'),1,12)` — never raw-key concat.

`PipelineStageService` provides create/update/reorder/deactivate (`CRM.STAGE.MANAGE`). An opportunity references exactly one **active** stage (`chk` enforced in service; the FK guarantees existence).

### D-7 — THE CONVERT SEAM (OQ-CRM-01/02): synchronous call into the shipped O2C services + an additive `source_opportunity_uid` back-link + a unique-constraint idempotency backstop

This is the one cross-module write and the load-bearing decision. **Adopt the synchronous service-call mechanism (option a) with the additive back-link column on the O2C documents (option a) — NOT an outbox event, NOT a CRM-side link table.**

**(1) The convert is a synchronous service call.** `OpportunityConversionService.convert(ConvertOpportunityRequest(opportunityUid, target ∈ {QUOTATION, SALES_ORDER}))`, in its own `@Transactional` method:
- guards the gate (D-7-(4)) + `assertCanActIn`;
- builds the O2C create request from the opportunity: for `QUOTATION` → `CreateQuotationRequest(companyUid, customerUid, agentUid, currency, quoteDate=today, validUntil=today+N (config/default), docDiscount…, notes)`; for `SALES_ORDER` → `CreateSalesOrderRequest(companyUid, customerUid, agentUid, currency, orderDate=today, docDiscount…, notes)` — passing **`sourceOpportunityUid`** (a new additive field on both create requests, D-7-(3));
- calls **`sales.service.QuotationService.create(req)`** or **`SalesOrderService.create(req)`** (returns the `QuotationDto`/`SalesOrderDto`), then for each `opportunity_line` calls the shipped **`addLine(...)`** with the line's product/qty/price/discount (the O2C `InvoiceTotalsCalculator` computes the real totals — CRM passes estimates, NFR-CRM-03);
- on success, stamps the opportunity: `converted_document_kind`, `converted_document_uid` (from the returned DTO), `converted_at`; the lead (if any) is already CONVERTED.

This is the **same outbound-service-call stance** `sales.service` takes to `stock.service`/`ar.service` and `ap.service` takes to `gl.service` — `crm → sales.service` returning a DTO, CRM importing no Sales entity (D-11). It is **synchronous** because the user expects to see the created quote/SO immediately (an async `OPPORTUNITY.WON` event would not return the document — rejected, Alternatives).

**(2) Idempotency via a unique DB constraint, not the outbox (NFR-CRM-02, BR-CRM-06).** Because the convert is synchronous (no event to dedup via `IdempotencyGuard`), idempotency is enforced by **`uq_opportunity_converted_document UNIQUE (converted_document_uid)`** + a **guard at the top of `convert`**: if `opportunity.converted_document_uid IS NOT NULL`, the convert is rejected with "already converted" (or returns the existing document DTO — the engineer's choice, both are idempotent). A retried/double-clicked convert thus creates the document **once**. (The O2C `create` itself is not naturally idempotent, so the CRM-side guard + the unique stamp is the mechanism; an integration test converts the same opportunity twice and asserts **one** quote/SO — NFR-CRM-02.)

**(3) The additive back-link on the O2C documents (V52).** Add one nullable column to each of `quotations` and `sales_orders`:

| table | column | type | null | notes |
|---|---|---|---|---|
| `quotations` | `source_opportunity_uid` | VARCHAR(26) | YES | the CRM opportunity it converted from; `ix_quotations_source_opportunity` partial index WHERE NOT NULL |
| `sales_orders` | `source_opportunity_uid` | VARCHAR(26) | YES | same; `ix_sales_orders_source_opportunity` partial index WHERE NOT NULL |

This mirrors ADR-0021's `sales_orders.source_quotation_uid` exactly (a scalar uid cross-doc trace, no FK across modules). The `CreateQuotationRequest`/`CreateSalesOrderRequest` records gain an **additive nullable `String sourceOpportunityUid`** field (defaulting null — existing direct-create callers are unaffected; the field is set only by the CRM convert). `QuotationServiceImpl.create`/`SalesOrderServiceImpl.create` persist it to the new column. **This is the only Sales touch CRM requires** — additive, surgical, within `sales` (CRM passes the uid; Sales stores it).

**(4) Convert gate + target (OQ-CRM-04, settled):** **OPEN may convert to a QUOTATION only** (quoting is part of negotiating; the opportunity stays OPEN, quote carries the back-link); **conversion to a SALES_ORDER requires `opportunity_status = WON`** (an SO is a commitment); a WON opportunity may convert to either. The gate is a service guard:
- `target = QUOTATION` → allowed when status ∈ {OPEN, WON};
- `target = SALES_ORDER` → allowed only when status = WON.
Owner may relax (a one-line guard change). **Archived/credit-blocked customer (OQ-CRM-05, settled):** CRM passes the customer uid; the O2C service applies its own validation (archived customer, credit limit at SO confirm — sales.md) and CRM **surfaces the O2C error** (it does not duplicate the validation).

#### Why convert cannot duplicate / cross-post

CRM owns no posting. The only effect is the O2C `create` call, guarded by the converted-document stamp + the unique constraint: a given opportunity produces **at most one** quote/SO (a second convert is rejected or returns the existing). The created document then runs the shipped O2C flow under its own controls (a quote is sent/accepted → SO; an SO is confirmed → reserves; the COGS/revenue postings are O2C's, ADR-0021). CRM introduces **no** new posting path, so there is **no double-post / phantom-GL surface** — the simplest correctness story of any module.

`CrmNumberGenerator` reuses the shipped `code_sequence` row-locked allocation (ADR-0007 D-6) with three new `entity_kind` values: `LEAD` (`LEAD-%04d`), `OPPORTUNITY` (`OPP-%04d`), `ACTIVITY` (`ACT-%04d`), per company, concurrency-safe (NFR-CRM-05). ### D-9 — Pipeline / forecast read model (FR-CRM-14)

## Consequences

**Positive**
- CRM ships the full pre-sales funnel (lead → qualify → opportunity → pipeline → activities → convert) as a **purely additive** module on the frozen V1–V19, touching **no money**: no GL post, no stock move, no AR item, no new gl_config/CoA/event. The simplest correctness story of any module.
- The Parties boundary is respected (BR-CRM-09): a lead holds its **own** contact data in CRM; a qualified lead **links/promotes** a Parties customer via the shipped `CustomerService.create`; **no Parties schema change**.
- The convert seam reuses the shipped O2C `QuotationService`/`SalesOrderService` exactly — CRM computes no money (NFR-CRM-03); the `InvoiceTotalsCalculator` does. The back-link is one additive nullable column per O2C document (mirroring `source_quotation_uid`), idempotent via a unique constraint + a convert guard (BR-CRM-06).
- Stage (configurable per-company FK master) and status (3-value enum) are clean orthogonal axes — filterable, reportable, never collapsed (BR-CRM-04).
- The change is surgical: 5 new tables, 1 per-company seeder + 1 #12-safe backfill, 2 additive O2C columns, 1 additive field on each of the 2 O2C create requests, 10 perms, 3 lazy numbering kinds, 4 ScopeGuard cases. **No cycle** (`crm → {parties, sales, products}`, one direction).

**Negative / costs**
- The convert touches `sales` in one release (the additive `source_opportunity_uid` column + the create-request field). It is additive on records/tables (defaulting null, existing callers unaffected), but it is a cross-module coordination point — flagged in the touch list. The synchronous convert means a Sales-service failure surfaces in the CRM convert request (the user sees the O2C error — OQ-CRM-05); acceptable (the user wants the document or the reason now).
- Idempotency rests on a CRM-side guard + a unique constraint, not the outbox `IdempotencyGuard` (because the convert is synchronous, not event-driven). The engineer must implement the convert guard exactly (reject/return-existing when already converted) — an integration test asserts one document on a double convert (NFR-CRM-02).
- The pipeline-stage backfill for existing companies is the one #12-vulnerable seed; it MUST use the md5-bounded form (V51-(6)) — documented to prevent a raw-key-concat regression.

**Neutral / deferred**
- Campaigns, email/SMS sync, case/ticket service, lead scoring/auto-assignment, contacts depth (the deferred Parties `contacts` table), rich dashboards, multi-currency/multi-agent opportunities — all deferred (§2), none precluded (NFR-CRM-06). The lead's `lead_source` + the activity timeline are the foundations a future campaign/email layer builds on; the pipeline read model is the data a future dashboard charts.

## Alternatives considered

- **The convert seam — synchronous service call (a) vs an `OPPORTUNITY.WON` outbox event (b).** *Decided: (a) synchronous call + the additive back-link column.* (b) decouples CRM from Sales but the user does not see the created quote/SO in the convert response (the event is consumed asynchronously by a Sales handler), which is a poor UX for an explicit "convert" action, and it needs a new `DomainEventType` + a Sales-side handler + the payload — more surface for no benefit at v1's scope. (a) is the shipped `ap → gl` / `sales → stock` outbound-call stance, returns the document immediately, and is made idempotent by the unique `converted_document_uid` + the convert guard. Reject (b).
- **The convert back-link — additive column on the O2C documents (a) vs a CRM-side `opportunity_conversions` link table (b).** *Decided: (a) the additive `source_opportunity_uid` column.* (b) avoids any Sales change but adds a CRM table that duplicates a single uid pair and needs its own read on every "where did this quote come from" question; (a) mirrors ADR-0021's own `source_quotation_uid` exactly (one nullable column per document), is the natural place for the trace, and costs two additive columns. Reject (b) — the link belongs on the document that was produced.
- **Lead contact storage — CRM-owned columns (a) vs creating a Parties customer immediately (b) vs a new Parties `contacts` table (c).** *Decided: (a) CRM-owned columns until qualify.* (b) pollutes the customer master with unqualified prospects; (c) is the deferred contacts-depth feature (§2) and would change Parties (BR-CRM-09 forbids it). (a) keeps the lead's data in CRM and joins Parties only on qualify (link or promote). Reject (b)/(c).
- **Stage/status modelling — one combined enum (a) vs stage-FK + separate status-enum (b).** *Decided: (b).* A combined enum (e.g. QUALIFICATION/PROPOSAL/.../WON/LOST) conflates the *configurable per-company funnel position* with the *fixed lifecycle close* and cannot support per-company editable stages. (b) makes the stage a per-company FK master (editable, reorderable) and the status a clean 3-value enum — orthogonal, filterable, reportable. Reject (a).
- **Owner/assignee FK target — `app_users` (a) vs `agents` (b).** *Decided: (a) `app_users` for owner/assignee, with `agents` captured separately on the opportunity for commission continuity.* The person who logs in and works the deal is an app_user; the commission-bearing agent is carried so the converted quote/SO has its agent (sales.md mandatory agent). Storing only the agent (b) would not identify the logged-in worker for the task list. Reject (b)-only (OQ-CRM-07).

## Staged build split (the increment is M-L — crm.md §10)

**Stage 1 — the pipeline core (no convert):**
- Tables: `pipeline_stages`, `leads`, `opportunities`, `opportunity_lines`, `activities` (V51).
- Code: the five entities + services + controllers; `CrmNumberGenerator` (LEAD/OPPORTUNITY/ACTIVITY kinds); `CrmStageSeeder` (per-company default stages) + the V51 backfill; the lead qualify-promote call into `parties.service.CustomerService.create`; the pipeline/forecast/KPI read (`PipelineQuery`); the four ScopeGuard cases.
- Permissions: `CRM.LEAD.*`, `CRM.OPPORTUNITY.{VIEW,MANAGE}`, `CRM.ACTIVITY.*`, `CRM.PIPELINE.VIEW`, `CRM.STAGE.MANAGE`. Self-contained CRM with **no cross-module write** beyond the qualify-promote call.

**Stage 2 — the convert seam into O2C:**
- Migration: `V52__crm_o2c_backlink.sql` (the two additive `source_opportunity_uid` columns + indexes).
- Code: `OpportunityConversionService` (the synchronous call into `QuotationService`/`SalesOrderService.create` + `addLine`); the additive `sourceOpportunityUid` field on `CreateQuotationRequest`/`CreateSalesOrderRequest` + its persistence in the two O2C `create` impls; the convert guard + `uq_opportunity_converted_document`.
- Permission: `CRM.OPPORTUNITY.CONVERT`. This is the one cross-module effect and the load-bearing seam.

## Summary

ADR-0031 designs the **CRM module** in a new `com.erp.modules.crm`: five tables (`pipeline_stages`, `leads`, `opportunities` + `opportunity_lines`, `activities`), three lifecycle enums (`LeadStatus`, `OpportunityStatus` OPEN/WON/LOST, `ActivityType`) plus `LeadSource`, configurable per-company pipeline stages (seeded + editable, with default probabilities), opportunities against a Parties customer with a stage-FK + status-enum **orthogonal-axes** model, activities/tasks against exactly one lead-or-opportunity parent, a pipeline/forecast/KPI read model, and **the convert seam** — a **synchronous** `crm.service → sales.service` call into the shipped `QuotationService.create` / `SalesOrderService.create` (+ `addLine`), idempotent via a unique `converted_document_uid` + a convert guard, recorded by an additive `source_opportunity_uid` back-link column on `quotations`/`sales_orders` (mirroring ADR-0021's `source_quotation_uid`). **CRM posts NO GL, moves NO stock, opens NO AR, introduces NO gl_config key / CoA account / DomainEventType / movement type** — it reads Parties (`CustomerService.create` to promote a qualified lead, no Parties schema change) and feeds Sales (convert). **Migration:** `V51__crm.sql` (the module + #12-safe pipeline-stage backfill + perms) + `V52__crm_o2c_backlink.sql` (the two additive O2C columns). **Additive on frozen V1–V19. No cycle** (`crm → {parties, sales, products}`, one direction). **Cross-module touch list:** (1) **crm → parties** — the qualify-promote `CustomerService.create` call; (2) **crm → sales** — the convert `QuotationService`/`SalesOrderService.create` call + the additive `source_opportunity_uid` column + create-request field; (3) **crm → products** — the opportunity-line price/product DTO read. **Readiness:** the ADR is concrete enough to build V51/V52 + the full model + the convert seam + the pipeline read without guessing a rule — every table, column, constraint name, enum, transition, convert mechanism, idempotency anchor, perm, ScopeGuard case, nav route, and seed is specified.
