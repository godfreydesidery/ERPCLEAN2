This ADR is the **technical data model** for the Stock module. It translates the ratified business spec
([stock.md](../requirements/stock.md)) and the outbox foundation ([ADR-0009](0009-transactional-outbox.md)) into
tables, columns, types, keys, indexes, constraints, the four event-consumer handlers, the recipe-explosion
algorithm, the idempotency mechanism, the enforcement split, the permission catalogue, the audit emit points, and
the two manual endpoints — **concrete enough that the backend engineer builds `V7__stock.sql`, the
`com.erp.modules.stock` entities, and the four `DomainEventHandler` impls without guessing a business rule.** It
does **not** write production code, entities, or the migration — that is the engineer's next step. The owner's
ratified v1 decisions (maintained on-hand row + append-only ledger; overselling allowed and flagged, never blocked;
six movement types (the GOODS_RECEIPT_REVERSAL mirror of SALE_REVERSAL added to consume ADR-0011's GR-void
compensating event) with TRANSFER reserved-but-deferred; recipe explosion on SALE_ISSUE with non-stockable
components skipped-and-recorded; quantity-only, no valuation; manual ADJUSTMENT with a mandatory reason from a fixed
list and no approval threshold; manual OPENING_BALANCE; optional indicator-only reorder level; idempotent
consumption keyed on the source event uid) are taken as given and designed to exactly. **Nothing ratified is
re-litigated.** This ADR depends on **ADR-0009** being built first (V6) — Stock is its first consumer.

## Context

Stock is the module that closes the sale→stock loop Sales shipped with an open seam (sales.md §1, ADR-0008 D-9:
the `// TODO(stock)` finalise seam). It holds **how much of each stockable product is at each branch right now**
(on-hand) and the **append-only history of every movement** that changed it. It is also the system's **first
event consumer**: it does not act on a user request to deduct stock — it reacts, as the system, to `SALE.FINALISED`
/ `SALE.VOIDED` / `STOCK.RECEIVED` events the outbox (ADR-0009) delivers. The central architectural forces:

- **Two structures, one transaction (OQ-STOCK-01 RESOLVED = maintained row + ledger).** The owner ruled **both**: a
  maintained **on-hand level** per (company, branch, stockable product) for the fast authoritative read, **and** an
  **append-only movement ledger** from which on-hand is reconstructable (FR-STOCK-03, BR-STOCK-01). The invariant
  is **on-hand == Σ its movements at all times** (BR-STOCK-01, NFR-STOCK-02 — a divergence is an inventory-grade
  defect). This forces every posted movement and the matching on-hand delta into the **same transaction**, with the
  on-hand row updated under a concurrency-safe mechanism (NFR-STOCK-04 — no lost update under two concurrent
  receipts, or a receipt racing an issue).

- **Idempotency is the single biggest correctness risk (NFR-STOCK-03, the release blocker).** The outbox is
  **at-least-once** (ADR-0009 D-4): a crash between "handler succeeded" and "event marked DISPATCHED" redelivers the
  event. A redelivered `SALE.FINALISED` must **not** deduct stock twice (FR-STOCK-13, BR-STOCK-08). ADR-0009 D-6
  provides a generic `processed_events` marker (a, the primary mechanism) and **referred to this ADR** to define
  Stock's `source_event_uid` backstop (b, the inventory-grade DB layer). This ADR defines (b) and how the two
  layers compose.

- **Overselling allowed, never blocked (OQ-STOCK-02 RESOLVED).** On-hand may go **negative**; a SALE_ISSUE that
  drives it below zero **still posts**, and the negative level is **flagged**, never prevented (FR-STOCK-04,
  BR-STOCK-03). This is load-bearing for the schema: the on-hand quantity column is **signed** (no `>= 0` CHECK),
  and "negative" is a derived/queryable read, not a forbidden state. Sales stays stock-agnostic (it never waits on
  a stock check — sales.md FR-SALES-21).

- **Recipe explosion is the one genuinely new piece of consumer logic (OQ-STOCK-03 RESOLVED).** A `SALE.FINALISED`
  line for a **composed** product (Products §9) must deduct its **stockable components** (qty = line `qtyInBase` ×
  recipe component quantity, in the component's base unit), **not** the composed product itself; a **non-stockable**
  component is **skipped and the skip recorded** (FR-STOCK-08, BR-STOCK-04). Products is single-level (FR-PROD-16),
  so no recursion arises. Stock reads the recipe + per-product stockable facts from Products **via DTO** (the same
  cross-module read pattern Sales uses), never importing a Products entity.

- **Quantity-only — NO valuation anywhere (RATIFIED, §10).** No movement row, no on-hand row, no report carries a
  money value (BR-STOCK-10, FR-STOCK-16). The model must capture quantity facts losslessly **and must not preclude**
  later per-movement cost capture / a valuation method / COGS (NFR-STOCK-06) — the clean additive change later is a
  nullable `unit_cost`/`Money` column on the movement, reserved, not built.

- **The consumer acts as the system, under the event's tenant scope — not a logged-in user (stock.md §4, ADR-0009
  D-5).** There is no JWT, no request-scoped `RequestContext` branch when the dispatcher runs. The handler must
  establish the working company/branch **from the event's `company_id`/`branch_id`** before it writes a movement
  (so the movement is tenant-correct and the `AuditService` — which resolves actor/company/branch from
  `RequestContext` — has a scope to record). Manual movements (ADJUSTMENT, OPENING_BALANCE) **do** act under a
  logged-in user's `RequestContext` and `assertCanActIn`. The model must serve both actor kinds.

- **Schema freeze / migration ordering.** IAM=V1, Parties=V2, Products=V3, Units=V4, Sales=V5, **Outbox=V6**
  (ADR-0009, built this round before Stock). Stock is a **new** module landing as a purely **additive
  `V7__stock.sql`**; it must not edit V1–V6. Its FK targets (`companies`, `branches`, `products`, `app_users`) all
  exist in frozen V1/V3. It depends on V6's `domain_events`/`processed_events` existing **as runtime infrastructure**
  but, deliberately, **takes no FK into `domain_events`** (D-5 — cross-cutting plumbing; the link is the
  `source_event_uid` string, not a coupling FK).

## Decision

### D-1 — Module placement: one `com.erp.modules.stock` module; the four event handlers live here and implement `platform.events.DomainEventHandler`

Stock lives in a **single** module `com.erp.modules.stock` with the standard internal layout:

```
com.erp.modules.stock
├── domain.entity   StockOnHand, StockMovement
├── domain.dto      StockOnHandDto, StockOnHandSummaryDto, StockMovementDto,
│                   AdjustStockRequest, OpeningBalanceRequest, StockLevelQuery, …
├── domain.enums    MovementType (GOODS_RECEIPT | SALE_ISSUE | SALE_REVERSAL | GOODS_RECEIPT_REVERSAL |
│                   ADJUSTMENT | OPENING_BALANCE; reserved TRANSFER_OUT | TRANSFER_IN — DEFERRED, OQ-STOCK-08),
│                   AdjustmentReason (the fixed reason list, D-7; D-6 movement-direction is derived, not stored)
├── repository      StockOnHandRepository, StockMovementRepository
├── service         StockService(+Impl)            — the manual ops (adjust, opening balance) + reads,
│                   StockPostingService(+Impl)      — the single internal "post a movement + update on-hand
│                                                     in one TX" primitive every path funnels through (D-4),
│                   RecipeExplosionResolver         — reads products.domain.dto, expands a composed line (D-8)
└── events          SaleIssueStockHandler           implements DomainEventHandler, eventType()=SALE.FINALISED
                    SaleReversalStockHandler        implements DomainEventHandler, eventType()=SALE.VOIDED
                    GoodsReceiptStockHandler         implements DomainEventHandler, eventType()=STOCK.RECEIVED
                    GoodsReceiptReversalStockHandler implements DomainEventHandler, eventType()=STOCK.RECEIPT.VOIDED
```

**Why `stock`, not `inventory`:** the requirements file, the vocabulary, and the owner all say "stock / on-hand /
stock movement" (stock.md §3). `inventory` is a vaguer umbrella that would compete with future valuation/costing
naming. `stock` is the durable name and matches the module-named-for-its-dominant-noun precedent (ADR-0007 D-1,
ADR-0008 D-1). Controllers stay flat in `com.erp.api` — `StockController` (on-hand views + the two manual
movement endpoints, D-11) — and touch only services (PROJECT-CONVENTIONS §2; `ModuleBoundaryTest`).

> **Boundary note for `ModuleBoundaryTest` (this is the headline boundary statement of the ADR).** Stock creates
> **no module→module entity edge**:
> - **It consumes the outbox by implementing `platform.events.DomainEventHandler`** (a platform interface — ADR-0009
>   D-1/D-5, on the `ModuleBoundaryTest` allow-list alongside `platform.security`/`audit`/`common`). The dispatcher
>   discovers the four handler beans by Spring DI; **Sales/Purchases never depend on Stock and Stock never depends
>   on Sales/Purchases** — the only thing that flows is the `DomainEvent` (a plain row: event-type string + a JSONB
>   payload of scalars and uids), not another module's entity. The `event` package is inside `com.erp.modules.stock`
>   but depends only on `platform.events` (the interface + `DomainEvent`) and Stock's own service.
> - **It reads Products via DTO only** — exactly the boundary Sales uses (ADR-0008 D-1). The recipe explosion + the
>   per-product stockable/base-unit facts come through **`ProductService`** returning `products.domain.dto`
>   (`ProductDto`, `ProductComponentDto`), never `products.*.entity` or `ProductComponentRepository`. The product
>   references Stock persists are **scalar `Long` `product_id`** columns with a real DB FK to `products(id)` — the
>   same SQL-only-FK / no-cross-module-`@ManyToOne` convention `sales_invoice_lines.product_id` already uses.
> - **No new boundary allow-list entry is required** — `platform.events` was added to the allow-list by ADR-0009;
>   Products DTO reads are already permitted (Sales established the precedent). The one new ArchUnit-relevant fact is
>   that Stock's `events` package implements `platform.events.DomainEventHandler` — a platform interface, allowed.

### D-2 — `stock_on_hand`: the maintained current level per (company, branch, stockable product), signed quantity, optional reorder level

A maintained level table — **one row per (company, branch, product)** that is or has ever been stocked at that
branch (FR-STOCK-01, BR-STOCK-01/07). Plural per the shipped convention. It is **not** a `UidEntity` master — it is
a maintained projection of the ledger, addressed in the API by its `(company, branch, product)` natural key (the
product uid + active branch), so it carries **no human `code`** and **no `code_sequence` row**. It **does** carry a
`uid` (ULID) so a specific on-hand row is uid-addressable in the API (e.g. the reorder-level edit, D-11) and so it
fits the system's uid/id duality (ADR-0001 D-G).

#### `stock_on_hand`

| column | type | null? | notes |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | NO | internal key |
| `uid` | `VARCHAR(26)` | NO | ULID; `uq_stock_on_hand_uid`; uid-addressed for the reorder-level edit (D-11) |
| `company_id` | `BIGINT` | NO | FK → `companies(id)`; tenant scope (BR-STOCK-07, NFR-STOCK-01); **never updated** |
| `branch_id` | `BIGINT` | NO | FK → `branches(id)`; the branch this level is held at (BR-STOCK-07); **never updated** |
| `product_id` | `BIGINT` | NO | FK → `products(id)` (scalar; **only a stockable product** — service invariant D-3/D-10, BR-STOCK-02) |
| `quantity` | `NUMERIC(19,6)` | NO | **signed** on-hand in **base units**; DEFAULT 0; **may be negative** (FR-STOCK-04, BR-STOCK-03) — **NO `>= 0` CHECK** (overselling allowed); scale 6 = shipped quantity convention (ADR-0007 D-3) |
| `reorder_level` | `NUMERIC(19,6)` | **YES** | optional per-(product, branch) low-stock **indicator** threshold (OQ-STOCK-06); NULL = no threshold; **indicator-only, no auto-reorder**; CHECK `>= 0` when present |
| `version` | `BIGINT` | NO | optimistic lock; DEFAULT 0 — **the lost-update guard** for concurrent movements against this row (NFR-STOCK-04, D-4) |
| `created_at` / `created_by` / `updated_at` / `updated_by` | `TIMESTAMPTZ` / `BIGINT` | mixed | standard audit columns (`*_by` → `app_users.id`; NULL `*_by` for system/event-driven updates — D-9) |

**Constraints on `stock_on_hand`:**
- `uq_stock_on_hand_uid UNIQUE (uid)`.
- **`uq_stock_on_hand_scope UNIQUE (company_id, branch_id, product_id)`** — exactly one on-hand row per
  (company, branch, product) (FR-STOCK-01, BR-STOCK-01). This is **the** key the posting primitive upserts on
  (D-4) and the natural identity of an on-hand level.
- `fk_stock_on_hand_company`, `fk_stock_on_hand_branch`, `fk_stock_on_hand_product` (→ `products`).
- **No CHECK on `quantity` sign** — overselling allowed (BR-STOCK-03). Negative is a valid, flagged state, not a
  violation.
- `chk_stock_on_hand_reorder CHECK (reorder_level IS NULL OR reorder_level >= 0)`.

**Indexes:**
```
-- the scope unique already indexes the (company, branch, product) probe — the hot upsert/read path.
CREATE INDEX ix_stock_on_hand_company_branch ON stock_on_hand (company_id, branch_id);   -- "on-hand at my active branch" (FR-STOCK-11)
CREATE INDEX ix_stock_on_hand_product        ON stock_on_hand (product_id);              -- "this product across branches"
-- negative-stock flag surfacing (FR-STOCK-04) — a small partial index over the negative working set.
CREATE INDEX ix_stock_on_hand_negative       ON stock_on_hand (company_id, branch_id) WHERE quantity < 0;
```

> **Why a maintained row AND a ledger, not pure-derived (OQ-STOCK-01, the recommendation the owner ratified):** a
> pure-derived on-hand (`SELECT SUM(quantity) FROM stock_movements WHERE …`) keeps a single source of truth but makes
> every POS on-hand read an aggregate scan over an append-heavy ledger (NFR-STOCK-08 fails as history grows). A
> maintained row gives the O(1) read; the ledger gives the immutable history and the reconciliation backstop. The
> cost — the two can diverge if a movement is posted without its on-hand delta — is contained by the **same-TX
> posting primitive (D-4)**, the **optimistic `version`** (no lost update), and an **integration test asserting
> on-hand == Σ movements after every operation** (NFR-STOCK-02). This is the same "maintained projection + immutable
> source, kept consistent in one TX, test-pinned" discipline the audit trail and the sales totals already use.

> **Why `reorder_level` lives on `stock_on_hand`, not on `products`:** the threshold is per-(product, **branch**)
> (a product reorders at a different level in a busy branch than a quiet one), and it is **indicator-only** with no
> auto-reorder (OQ-STOCK-06). A nullable column on the (company, branch, product) row is the boring home; it is set
> via a small admin path under `STOCK.ADJUST` (D-11) and is **the only mutable non-quantity field** on the row. A
> per-product default that branches inherit is a future additive convenience, not built (flagged).

### D-3 — Only a stockable product has on-hand and moves (BR-STOCK-02) — service-enforced, DTO-sourced from Products

There is **no on-hand row and no movement** for a non-stockable product or a service (FR-STOCK-02, BR-STOCK-02).
Products owns the `stockable` fact; Stock reads it via `ProductService.getByUid(productUid) → ProductDto.stockable()`
(the shipped DTO carries it). The rule is enforced in the **service** at every entry point:

- **Manual ADJUSTMENT / OPENING_BALANCE (D-11):** the service reads the target product's `ProductDto`; if
  `!stockable`, it **rejects** (422 — "not a stockable product"). It also asserts the product belongs to the active
  company (cross-module same-company, service-enforced — mirrors ADR-0007/0008 D-10).
- **Event-driven SALE_ISSUE / SALE_REVERSAL (D-5/D-8):** a line naming a **non-stockable** product (and not
  composed) posts **no** movement — it is **skipped and the skip recorded** (FR-STOCK-08, BR-STOCK-02, §7.5; the
  skip-record is a DEBUG/INFO log + the absence of a movement, not a movement row — D-9 audit note). A **composed**
  product line is exploded (D-8); its **non-stockable components are skipped-and-recorded**, stockable ones
  deducted.
- **Event-driven GOODS_RECEIPT (D-5):** Purchases only receives stockable goods onto stock; a defensive
  `!stockable` line is skipped-and-recorded (Purchases should not emit it; Stock does not trust the producer
  blindly).

A DB FK to `products` cannot assert `stockable = true` (it is a column on the parent, not the FK target identity) —
this is the standard DB-can't / service-must split (ADR-0006 D-4, ADR-0007 D-9). The `product_id` FK guarantees the
product exists; the service guarantees it is stockable.

### D-4 — `stock_movements`: the append-only ledger; on-hand maintained in the SAME transaction via a single posting primitive

The immutable history — **one row per posted change to on-hand** (FR-STOCK-05, BR-STOCK-06). Every path that
changes stock (the four event handlers + the two manual ops) funnels through **one internal primitive**,
`StockPostingService.post(...)`, which in **one transaction**: (1) appends the `stock_movements` row, and (2)
upserts the matching `stock_on_hand` row's `quantity` by the signed delta (creating the on-hand row at quantity 0
on first touch, then applying the delta), under the optimistic `version` (retry-once on a version clash;
NFR-STOCK-04). This is the single place the BR-STOCK-01 invariant (on-hand == Σ movements) is kept true, so it is
the single place to test and review.

#### `stock_movements`

| column | type | null? | notes |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | NO | internal key |
| `uid` | `VARCHAR(26)` | NO | ULID; `uq_stock_movement_uid`; a movement is uid-addressed in the ledger drill-down (D-11) |
| `company_id` | `BIGINT` | NO | FK → `companies(id)`; tenant scope (BR-STOCK-07, NFR-STOCK-01); **never updated** |
| `branch_id` | `BIGINT` | NO | FK → `branches(id)`; the branch the movement occurred at (BR-STOCK-07); **never updated** |
| `product_id` | `BIGINT` | NO | FK → `products(id)` (scalar; stockable — D-3); the product whose on-hand this row changed |
| `movement_type` | `VARCHAR(25)` | NO | `GOODS_RECEIPT` \| `SALE_ISSUE` \| `SALE_REVERSAL` \| `GOODS_RECEIPT_REVERSAL` \| `ADJUSTMENT` \| `OPENING_BALANCE`; CHECK below (FR-STOCK-05). TRANSFER_* reserved in the enum, **NOT** in the CHECK (deferred — OQ-STOCK-08) |
| `quantity` | `NUMERIC(19,6)` | NO | **signed** delta in **base units** (+ in, − out); CHECK `<> 0` (a zero movement is meaningless); scale 6 (ADR-0007 D-3). Sign convention by type: D-6 |

| `note` | `VARCHAR(500)` | YES | optional free-text on a manual movement (e.g. an adjustment explanation); the anomaly note for an unmatched SALE_REVERSAL (D-5, OQ-STOCK-10) |
| `occurred_at` | `TIMESTAMPTZ` | NO | DEFAULT `now()`; when the movement happened (= the event's `finalisedAt`/receipt time for event-driven, or post-time for manual); the ledger ordering key |
| `created_at` / `created_by` | `TIMESTAMPTZ` / `BIGINT` | mixed | append-only audit columns; `created_by` = the operator (manual) **or NULL** (system/event-driven — D-9). **No `updated_*`** — a movement is never edited (BR-STOCK-06) |

**Constraints on `stock_movements`:**
- `uq_stock_movement_uid UNIQUE (uid)`.
- **`uq_stock_movement_source_event UNIQUE (source_event_uid, product_id)`** — **the inventory-grade idempotency
  backstop (ADR-0009 D-6b).** Postgres treats NULLs as distinct, so the many manual movements (NULL
  `source_event_uid`) coexist; the constraint bites only for event-driven rows. It is keyed by
  `(source_event_uid, product_id)` — **not** `source_event_uid` alone — because **one** `SALE.FINALISED` event
  legitimately produces **many** movements (one per line, and one per stockable component of a composed line), each
  for a **distinct `product_id`** (D-8). The pair guarantees: a given (event, product) is deducted **at most once**,
  so a redelivered event cannot double-move any product, while still allowing the several products one event
  touches. (See D-5 for why this is a backstop, not the primary dedup, and the composed-product edge it handles.)
- `fk_stock_movement_company`, `fk_stock_movement_branch`, `fk_stock_movement_product` (→ `products`).
- `chk_stock_movement_type CHECK (movement_type IN ('GOODS_RECEIPT','SALE_ISSUE','SALE_REVERSAL','GOODS_RECEIPT_REVERSAL','ADJUSTMENT','OPENING_BALANCE'))`
  — **v1 admits only the six built types**; the `TRANSFER_OUT`/`TRANSFER_IN` enum values are reserved in Java but
  **excluded from the CHECK** so a stray transfer row cannot appear before the feature is built (widen the IN-list
  additively when TRANSFER lands — OQ-STOCK-08; same tight-CHECK-then-widen discipline as `sales_invoices.document_type`).
- `chk_stock_movement_qty CHECK (quantity <> 0)` — a movement always changes on-hand by a non-zero signed amount.
- **`chk_stock_movement_reason CHECK ((movement_type = 'ADJUSTMENT' AND reason_code IS NOT NULL) OR (movement_type <> 'ADJUSTMENT' AND reason_code IS NULL))`**
  — BR-STOCK-05: an ADJUSTMENT **must** carry a reason; no other type carries one. Single-row-expressible, so it
  lands at the DB (the service maps it to a friendly 422 and validates the value against the fixed `AdjustmentReason`
  enum — the CHECK enforces presence, the service enforces the value is in the list, D-7).
- **No `>= 0` CHECK on `quantity`** beyond `<> 0` — the **sign** is the direction, and a movement may be negative
  (SALE_ISSUE, GOODS_RECEIPT_REVERSAL, a negative ADJUSTMENT) or positive (GOODS_RECEIPT, SALE_REVERSAL,
  OPENING_BALANCE, a positive ADJUSTMENT). The on-hand consequence may go negative (BR-STOCK-03); the movement itself
  is just a signed delta.

**Indexes (the ledger is append-heavy; read paths are by product-at-branch and by source — NFR-STOCK-08):**
```
CREATE INDEX ix_stock_movements_product_branch ON stock_movements (company_id, branch_id, product_id, occurred_at);  -- THE drill-down: a product's history at a branch, chronological (FR-STOCK-11)
CREATE INDEX ix_stock_movements_company_branch ON stock_movements (company_id, branch_id, occurred_at);              -- branch movement feed
CREATE INDEX ix_stock_movements_source_doc     ON stock_movements (source_document_type, source_document_uid);       -- "all movements for this invoice/receipt" (the OQ-STOCK-10 reversal lookup, D-5)
-- the uq_stock_movement_source_event unique already indexes the (source_event_uid, product_id) idempotency probe.
```

> **Why `source_event_uid` is the idempotency key, not a generated movement number:** a movement has no
> human-facing number (it is ledger plumbing, not a document) — so **no `code_sequence` row and no `MOV-####`**.
> Its external identity is its ULID `uid`; its **provenance** is `source_event_uid` + `source_document_*`. The
> idempotency the spec demands (FR-STOCK-13) is keyed on the **source event uid** (the owner's exact ruling: "a
> movement is keyed by its source domain-event uid so event redelivery never double-applies"), which is precisely
> what `uq_stock_movement_source_event` enforces.

### D-5 — The four event-consumer handlers: `DomainEventHandler` impls, idempotent on the source event uid, acting under the event's tenant scope

All four handlers live in `com.erp.modules.stock.events`, implement `platform.events.DomainEventHandler` (ADR-0009
D-5), are discovered by the dispatcher via Spring DI, and run **inside the dispatcher's per-event transaction**
(ADR-0009 D-5) — so the movement(s), the on-hand delta(s), the `processed_events` marker, and the event's
`DISPATCHED` mark all commit together. **Every handler is idempotent** (the contract — ADR-0009 D-5/D-6).

**The common consumer skeleton (every handler follows it):**
1. **Establish the system tenant context from the event.** The handler reads `event.companyId` / `event.branchId`
   and sets a **system-scoped `RequestContext.Principal`** for the duration of the handle — a principal with
   `userId = null`, `root = false`, `companyId`/`branchId` from the event (a small `SystemRequestContext.runAs(...)`
   helper in `platform.security`, or set/clear around the body). This makes (a) the tenant predicate filter
   correctly when the handler reads/writes, and (b) the `AuditService` (which resolves company/branch from
   `RequestContext`) have the event's scope, with a **null actor** (system). This is the ADR-0009 D-5
   "tenant-context-from-the-event" rule made concrete; it is **not** the request `RequestContext` (no JWT).
   *(The exact helper is the engineer's; the requirement is: the handler writes its movement under the event's
   company/branch, as the system, never under a logged-in user.)*
2. **Dedup (the primary mechanism — ADR-0009 D-6a `processed_events`).** At the **start** of `handle`, attempt to
   insert `processed_events(consumer, event_uid)` with the handler's logical `consumer` name (D-6 below). If it
   already exists (unique-constraint collision on `uq_processed_event`), this is a **redelivery → return without
   applying any effect** (idempotent no-op). Because the marker insert and the movement(s) are in the same TX, they
   commit together (first delivery) or the marker collides (redelivery → skip).
3. **Apply the effect** by calling `StockPostingService.post(...)` once per resulting movement (D-4), each stamped
   with `source_event_uid = event.uid`, `source_document_type`/`source_document_uid` from the payload, and the
   per-type sign/`movement_type` (D-6). The **`uq_stock_movement_source_event (source_event_uid, product_id)`
   backstop (D-4)** is the **second layer**: even if the marker were somehow bypassed, a duplicate
   (event, product) movement is rejected by the DB — inventory-grade defence-in-depth (ADR-0009 D-6b).

The four handlers, each keyed by its `eventType()`:

**(1) `SaleIssueStockHandler` — `eventType() = DomainEventType.SALE_FINALISED`** (ADR-0009 `DomainEventType`).
Payload: `{ invoiceUid, companyId, branchId, finalisedAt, lines:[{ productId, productUid, unitId, qtyInBase }] }`
(ADR-0008 D-9, verbatim). For each line:
- read the line product's `ProductDto` (via `ProductService`, by `productUid`);
- **simple stockable** → post one `SALE_ISSUE` movement, `quantity = −qtyInBase` (out), `product_id` = the line
  product. (`qtyInBase` is already in base units — Sales snapshotted it, ADR-0008 D-2 — so **no live unit
  conversion** is needed.)
- **composed** (`product_components` rows exist — D-8) → **explode** (RecipeExplosionResolver): for each component,
  post a `SALE_ISSUE` of `quantity = −(qtyInBase × recipeComponentQty)` for the **stockable** component; **skip and
  record** a non-stockable component; **do not** post for the composed product itself (BR-STOCK-04, FR-STOCK-08).
- **non-stockable & not composed** → **skip and record** (no movement — BR-STOCK-02).
- `source_document_type = SALES_INVOICE`, `source_document_uid = invoiceUid`, `occurred_at = finalisedAt`.

**(2) `SaleReversalStockHandler` — `eventType() = DomainEventType.SALE_VOIDED`** (the compensating event). Payload:
the `SALE.VOIDED` shape (ADR-0008 D-9; same `invoiceUid` + lines). It posts **`SALE_REVERSAL` in-movements that
reverse exactly what the original SALE_ISSUE deducted** (OQ-STOCK-10 RESOLVED = reverse only what was issued). The
**authoritative source of "what was issued" is Stock's own ledger** — the handler looks up the prior movements by
`source_document_uid = invoiceUid AND movement_type = 'SALE_ISSUE'` (the `ix_stock_movements_source_doc` index) and
posts an opposite-sign `SALE_REVERSAL` for each (same product, same magnitude, sign flipped). This is robust to the
composed-product case automatically (the reversal mirrors the component issues the original explosion posted) and to
the out-of-order edge:
- **Void arrives but Stock never issued** (out-of-order / a sale whose lines were all non-stockable) → **nothing
  matches → post no phantom negative; record an anomaly** (a log + an optional `note`-bearing zero-effect marker is
  rejected by `chk_stock_movement_qty <> 0`, so the anomaly is a **log/metric**, not a movement row) — exactly the
  OQ-STOCK-10 ruling (ADR-0009 D-7). The handler still records the `processed_events` marker so the void is not
  re-attempted.
- `source_document_type = SALES_INVOICE`, `source_document_uid = invoiceUid` on each reversal.

> **Why reverse from Stock's own ledger, not from the void payload's lines:** the original explosion (composed →
> components) means the void payload's lines (the composed products) are **not** what was deducted (the components
> were). Reversing from the ledger (`SALE_ISSUE` rows for that invoice) reverses precisely what moved, including the
> exploded components, with no re-explosion and no risk of reversing a line that was skipped (non-stockable). This is
> the inventory-grade-correct reading of OQ-STOCK-10.

**(3) `GoodsReceiptStockHandler` — `eventType() = DomainEventType.STOCK_RECEIVED`** (from Purchases, ADR-0011 /
purchases.md FR-PURCH-08). Payload mirrors Sales: `{ receiptUid (aggregate uid), companyId, branchId, receivedAt,
lines:[{ productId, productUid, unitId, qtyInBase }] }`. For each line: post one `GOODS_RECEIPT` movement,
`quantity = +qtyInBase` (in), `product_id` = the line product, `source_document_type = GOODS_RECEIPT`,
`source_document_uid = receiptUid`, `occurred_at = receivedAt`. A **partial receipt** emits its **own** event with
its own uid (purchases.md FR-PURCH-08), so each partial posts its own idempotent movement (FR-STOCK-06). A defensive
non-stockable line is skipped-and-recorded (D-3).

**(4) `GoodsReceiptReversalStockHandler` — `eventType() = DomainEventType.STOCK_RECEIPT_VOIDED`** (the compensating
event Purchases emits on a Goods-Receipt void, ADR-0011 D-7). Payload mirrors `STOCK.RECEIVED`: `{ receiptUid,
companyId, branchId, lines:[{ productId, productUid, unitId, qtyInBase }] }` (ADR-0011). It is the **exact mirror of
`SaleReversalStockHandler` (2)** for the buying side: it posts **`GOODS_RECEIPT_REVERSAL` out-movements that reverse
exactly what the original GOODS_RECEIPT added** (OQ-STOCK-10 RESOLVED = reverse only what was applied — the same
reverse-only-what-was-issued principle, read as reverse-only-what-was-received). The **authoritative source of "what
was received" is Stock's own ledger** — the handler looks up the prior movements by `source_document_uid = receiptUid
AND movement_type = 'GOODS_RECEIPT'` (the `ix_stock_movements_source_doc` index) and posts an opposite-sign
`GOODS_RECEIPT_REVERSAL` for each (same product, same magnitude, sign flipped to **−**, i.e. stock back out). This is
robust to the out-of-order / nil-effect edge exactly as (2) is:
- **Void arrives but Stock never posted a GOODS_RECEIPT for that receipt** (out-of-order, or a receipt whose lines
  were all defensively-skipped non-stockable) → **nothing matches → post no phantom out-movement; record an anomaly**
  (a log/metric — a zero-effect movement is forbidden by `chk_stock_movement_qty <> 0`, so the anomaly is a
  log/metric, **not** a movement row) — the same OQ-STOCK-10 ruling as (2). The handler still records the
  `processed_events` marker so the void is not re-attempted.
- `source_document_type = GOODS_RECEIPT`, `source_document_uid = receiptUid` on each reversal; `source_event_uid` =
  the **void event's own uid** (so the `(source_event_uid, product_id)` backstop dedupes on the void, distinct from
  the original receipt event's uid that the GOODS_RECEIPT rows carry).
- Dedup `consumer` name `STOCK.GOODS_RECEIPT_REVERSAL` (D-6), keyed on the **void event's own uid** via
  `processed_events` (primary) and the `(source_event_uid, product_id)` movement backstop (secondary) — a redelivered
  void cannot double-reverse.

> **Why reverse from Stock's own ledger, not from the void payload's lines** (identical to (2)): reversing the
> `GOODS_RECEIPT` rows actually posted for that receipt reverses precisely what moved — including correctly **not**
> reversing a line that was skipped (a defensive non-stockable line never posted a GOODS_RECEIPT, so there is nothing
> to reverse), with no re-derivation from the payload. This is the inventory-grade-correct reading of OQ-STOCK-10 for
> the buying side, and it keeps (2) and (4) the same one-shaped handler. Stock's posting primitive (D-4) and
> idempotency (D-6) support it with **no schema change** beyond the added `GOODS_RECEIPT_REVERSAL` movement type
> (D-4/D-6).

### D-6 — Movement-type semantics: sign convention, direction derived not stored, and the `consumer` dedup names

**Sign convention (the `quantity` column is the signed delta — D-4):**

| `movement_type` | sign | source | `source_event_uid` | `reason_code` | `created_by` |
| --- | --- | --- | --- | --- | --- |
| `GOODS_RECEIPT` | **+** (in) | event `STOCK.RECEIVED` (Purchases GR) | set | NULL | NULL (system) |
| `SALE_ISSUE` | **−** (out) | event `SALE.FINALISED` (Sales finalise) | set | NULL | NULL (system) |
| `SALE_REVERSAL` | **+** (in) | event `SALE.VOIDED` (Sales void) | set | NULL | NULL (system) |
| `GOODS_RECEIPT_REVERSAL` | **−** (out) | event `STOCK.RECEIPT.VOIDED` (Purchases GR void) | set (the **void** event's uid) | NULL | NULL (system) |
| `ADJUSTMENT` | **±** (either) | manual (D-11) | NULL | **NOT NULL** (fixed list, D-7) | the operator |
| `OPENING_BALANCE` | **+** (in) | manual seed (D-11) | NULL | NULL | the operator |

- **Direction is derived from the sign, not stored as a separate column.** A separate `direction` enum would
  duplicate (and could drift from) the `quantity` sign. The on-hand consequence is always `quantity += movement.quantity`
  (D-4) — the sign carries direction. Reads that want a friendly "IN/OUT" badge derive it on the DTO (`quantity > 0`).
- **`OPENING_BALANCE` is always positive (an initial seed); `ADJUSTMENT` is the only ± type** (a count correction can
  be up or down). A negative OPENING_BALANCE is rejected by the service (a never-tracked product starts at ≥ 0;
  "we already had negative" is an ADJUSTMENT, not an opening balance).
- **The `processed_events.consumer` names (ADR-0009 D-6a)** — one per handler, so the four dedupe independently:
  `STOCK.SALE_ISSUE`, `STOCK.SALE_REVERSAL`, `STOCK.GOODS_RECEIPT`, `STOCK.GOODS_RECEIPT_REVERSAL`. (A future second
  consumer of `SALE.FINALISED` dedupes on its own `consumer` name, ADR-0009 D-6a.)

### D-7 — Adjustment reasons: a fixed `AdjustmentReason` enum, mandatory on ADJUSTMENT, no approval threshold

OQ-STOCK-04 RESOLVED = **small fixed reason list, reason mandatory, no approval threshold** (permission alone
gates). The reason is a **fixed enum** (`AdjustmentReason` in `stock.domain.enums`), stored as the
`reason_code VARCHAR(40)` string on the movement (the same enum-as-string discipline as every other enum column):

| `reason_code` | meaning |
| --- | --- |
| `COUNT_CORRECTION` | physical count differs from system (the stocktake-by-adjustment path, OQ-STOCK-07) |
| `DAMAGE` | stock written off as damaged |
| `SHRINKAGE` | loss / theft / spoilage |
| `EXPIRY` | written off past expiry (no batch/expiry tracking in v1 — this is the manual catch-all) |
| `RECEIPT_CORRECTION` | a manual fix to a mis-received quantity (when not done via a GR reversal) |
| `OTHER` | any other reason; the free-text `note` (D-4) should accompany it |

- The set is **owner-confirmable** (these are the recommended defaults; the owner may add/rename before build — a
  one-edit enum change, flagged below, not blocking). The **CHECK enforces presence** (`chk_stock_movement_reason`,
  D-4); the **service enforces the value is in the enum** (a value outside the list → 422). v1 deliberately does
  **not** add a DB `CHECK (reason_code IN (...))` enum-list constraint on the movement, because the reason list is
  expected to evolve (owner-tunable) and an enum-list CHECK would force a migration per reason added — the service
  validates the value; the CHECK only enforces presence-when-ADJUSTMENT. *(If the owner wants the list frozen, a
  `CHECK (reason_code IN (...))` is a trivial addition — flagged.)*
- **No approval threshold** (OQ-STOCK-04) — the `STOCK.ADJUST` permission alone authorises any adjustment magnitude.
  A future approval workflow (a pending→approved adjustment state) is deferred; the model does not preclude it.

### D-8 — Recipe explosion: read the single-level recipe + per-component stockable facts from Products via DTO

When a `SALE.FINALISED` line names a **composed** product, the `RecipeExplosionResolver` (in `stock.service`)
expands it (FR-STOCK-08, BR-STOCK-04, Products §9). The Products reads it needs, all via `ProductService` DTOs (the
boundary, D-1):

1. **Is the line product composed?** A product is composed iff it has `product_components` rows (Products derives
   "composed", does not store a flag — ADR-0007 D-8). Stock reads `ProductService.listComponents(productUid)`; a
   **non-empty** list ⇒ composed ⇒ explode; an **empty** list ⇒ simple ⇒ deduct the product itself (D-5).
2. **For each component** (`ProductComponentDto`: `componentProductId`, `componentProductUid`, `quantity`): the
   shipped `ProductComponentDto` carries the component's id/uid/code/name + recipe `quantity` but **not** the
   component's `stockable` flag or base unit. So the resolver reads each component's `ProductDto` (via
   `ProductService.getByUid(componentProductUid)`) to learn `stockable()`. **If stockable:** post a `SALE_ISSUE`
   of `quantity = −(line.qtyInBase × component.quantity)` (the recipe quantity is in the component's base units —
   Products FR-PROD-14; `qtyInBase` is the composed line in *its* base units; the product of the two is the
   component base-unit quantity to deduct). **If non-stockable:** skip and record (BR-STOCK-04).
3. **Single-level only** (FR-PROD-16) — a component that is *itself* composed is **not** recursively expanded in v1
   (Products is single-level; multi-level BOM is deferred, stock.md §12). The resolver explodes exactly one level:
   it deducts the direct components' on-hand, full stop.

> **Reservation / performance note:** the explosion does N+1 `ProductService.getByUid` reads per composed line (one
> per component) to learn `stockable`. For v1 volumes this is fine (recipes are small, the dispatcher is async — not
> on the sale's critical path). If it ever matters, the clean additive optimisation is to **enrich
> `ProductComponentDto` with the component's `stockable` flag + base unit** (a Products DTO change, no Stock schema
> change), so the explosion needs only the one `listComponents` call. Recommended as the engineer's call if the
> per-component read is awkward; flagged, non-blocking. *(I recommend enriching `ProductComponentDto` with
> `componentStockable` — it is the cleaner long-term shape and saves the N+1; it is an additive Products DTO field.)*

### D-9 — Enforcement split (DB vs service) and the "skip recorded" treatment

Consistent with ADR-0006 D-6 / ADR-0007 D-9 / ADR-0008 D-10 (DB enforces unconditional/single-row; service enforces
cross-row / cross-module / conditional):

| rule | enforcement | mechanism |
| --- | --- | --- |
| BR-STOCK-01 on-hand == Σ movements | **service + test** | `StockPostingService` posts movement + on-hand delta in **one TX** (D-4); IT asserts equality after every op (NFR-STOCK-02) |
| BR-STOCK-02 only a stockable product moves | **service** | reads `ProductDto.stockable` via `ProductService`; non-stockable → skip+record (event) or 422 (manual) (D-3) |
| BR-STOCK-03 negative on-hand allowed, never blocked | **by design (DB)** | **no `>= 0` CHECK** on `stock_on_hand.quantity` (D-2); negative is a flagged, queryable state (partial index) |
| BR-STOCK-04 composed → explode to components, skip non-stockable | **service** | `RecipeExplosionResolver` reads the recipe + component stockable via DTO (D-8) |
| BR-STOCK-05 ADJUSTMENT requires a reason + permission | **DB CHECK + service** | `chk_stock_movement_reason` (presence); service validates the value in `AdjustmentReason` + `STOCK.ADJUST` gate (D-7/D-11) |
| BR-STOCK-06 movements are append-only | **DB + ArchUnit** | `stock_movements` has **no `updated_*`**; `StockMovementRepository` exposes no update/delete (interface narrowed, mirroring the audit append-only rule); a compensating movement corrects, never an in-place edit |
| BR-STOCK-07 stock belongs to one company + one branch | **DB** | `company_id`/`branch_id` NOT NULL + FKs on both tables; never updated; the §3.2 tenant predicate |
| BR-STOCK-08 each event drives its effect exactly once | **DB + service** | `processed_events` marker (ADR-0009 D-6a) **and** `uq_stock_movement_source_event (source_event_uid, product_id)` backstop (D-4/D-6b); each of the four handlers dedupes on its own event's uid under its own `consumer` name (D-6) |
| BR-STOCK-09 quantities in base units | **service** | event payloads carry `qtyInBase` (Sales/Purchases convert at source); manual ops enter base units; the recipe math is base × recipe-qty (D-8) |
| BR-STOCK-10 no valuation in v1 | **by design** | no money column anywhere on `stock_on_hand`/`stock_movements`; reserved additive `unit_cost` for later (NFR-STOCK-06) |
| movement quantity non-zero; type ∈ enum | **DB CHECK** | `chk_stock_movement_qty`, `chk_stock_movement_type` (D-4) |
| reorder_level ≥ 0 when present | **DB CHECK** | `chk_stock_on_hand_reorder` (D-2) |

- **"Skip recorded" is a log/metric, not a movement row** (D-3/D-5). A non-stockable line, a non-stockable
  component, or a no-match reversal (an unmatched `SALE.VOIDED` or `STOCK.RECEIPT.VOIDED`) produces **no
  `stock_movements` row** (a zero-effect movement is forbidden by `chk_stock_movement_qty <> 0`, and a movement row
  should mean "stock moved"). The "record" is an **INFO/DEBUG log line + a metric counter** (e.g.
  `stock.skip.nonstockable`, `stock.void.unmatched`) so the skip is traceable and alertable, per stock.md §7.5 /
  OQ-STOCK-03/10 — the movement ledger stays a clean record of *actual* movements,
  and the **outbox's `domain_events` row** (DISPATCHED, with its payload) is the durable record that the event *was*
  processed even when its net stock effect was nil. (No new "skip log" table in v1 — the existing event row + the
  log/metric are sufficient; a structured skip-audit table is a future additive option if traceability demands it,
  flagged.)

### D-10 — `ScopeGuard.companyIdOf`: add `stockonhand` and `stockmovement` target types

The 2-arg `@perm.scoped(#uid, 'stockonhand', 'STOCK.ADJUST')` gate needs `ScopeGuard.companyIdOf` to resolve a
stock-on-hand uid (and a movement uid, for the ledger drill-down view) to its company — exactly the extension
ADR-0007 D-10 / ADR-0008 D-10 made. The engineer adds to the `companyIdOf` switch
([ScopeGuard.java](../../backend/src/main/java/com/erp/platform/security/ScopeGuard.java) lines 85–99):

```java
case "stockonhand"  -> stockOnHand.findCompanyIdByUid(uid);
case "stockmovement" -> stockMovements.findCompanyIdByUid(uid);
```

backed by single-column JPQL projections on `StockOnHandRepository` / `StockMovementRepository`
(`@Query("SELECT s.companyId FROM StockOnHand s WHERE s.uid = :uid")`), mirroring the eleven existing cases. This
adds two repository constructor dependencies to `ScopeGuard` — the same cross-cutting-spine pattern already accepted
for the product/party/sales repositories (ScopeGuard is the security spine, ArchUnit-allowed). **Not optional** —
without it the target-uid gates fail closed.

- **Most Stock operations gate by the active company/branch, not by a target uid.** The on-hand list and the
  adjustment/opening-balance creates address the **active branch** (from `RequestContext`) for a **product uid**
  (resolved to its company via the existing `'product'` case), so they use `@perm.scoped(#request.productUid,
  'product', 'STOCK.ADJUST')` + an in-service `assertCanActIn(principal, product.companyId)` + the branch-from-context
  discipline (D-11). The `'stockonhand'` target type is for the **reorder-level edit** (which addresses an existing
  on-hand row by its uid); `'stockmovement'` is for a single-movement read. Both are added for completeness so any
  uid-addressed stock op fails closed correctly.

### D-11 — Manual movement endpoints (`StockController`, flat in `com.erp.api`), permission-gated, branch-from-context

Two manual write operations + the read surface. The event-driven movements (receipt/issue/reversal) are posted by
the **system event consumer** (D-5) under the originating event's authority — there is **no REST endpoint** for them
(FR-STOCK-15). The manual endpoints:

- **`POST /stock/adjustments`** — record an ADJUSTMENT (FR-STOCK-09, §7.4). Body `AdjustStockRequest`:
  `{ productUid, quantity (signed, base units), reasonCode (AdjustmentReason), note? }`. The **branch is the
  operator's active branch from `RequestContext`** (NOT in the body — same discipline as ADR-0008 D-12: an operator
  may only adjust at the branch they are in; a body `branchUid` would let them adjust elsewhere). Gate:
  `@PreAuthorize("@perm.scoped(#request.productUid, 'product', 'STOCK.ADJUST')")`; the service additionally
  `assertCanActIn(principal, product.companyId)`, asserts `product.stockable` (D-3), validates `reasonCode` in the
  enum (D-7), and posts via `StockPostingService` (D-4). Audited (D-12).
- **`POST /stock/opening-balances`** — seed an OPENING_BALANCE for a never-tracked (product, active branch)
  (FR-STOCK-10, OQ-STOCK-05 = manual). Body `OpeningBalanceRequest`: `{ productUid, quantity (positive, base
  units), note? }`. Gate: `@PreAuthorize("@perm.scoped(#request.productUid, 'product', 'STOCK.OPENING')")`; service
  asserts `product.stockable`, asserts the (product, active branch) has **no prior movements** (an opening balance
  seeds a *never-tracked* level — a second opening balance is rejected; subsequent corrections are ADJUSTMENTs),
  rejects a non-positive quantity (D-6), posts via `StockPostingService`. Audited.
- **Reads (`GET`):**
  - `GET /stock/on-hand` — list/search current on-hand at the **active branch** (FR-STOCK-11), paged via `PageMeta`,
    each row carrying a **derived `negative`/`low` flag** (`quantity < 0` / `reorder_level IS NOT NULL AND quantity
    <= reorder_level` — computed on the DTO, not stored). Gate `@PreAuthorize("hasAuthority('STOCK.VIEW')")`, results
    scoped by the tenant predicate + active branch.
  - `GET /stock/on-hand/uid/{uid}/movements` (or `GET /stock/products/uid/{productUid}/movements`) — the movement
    ledger drill-down for a product at the active branch (FR-STOCK-11), chronological, paged. Gate `STOCK.VIEW`.
  - `PUT /stock/on-hand/uid/{uid}/reorder-level` — set/clear the optional reorder level (OQ-STOCK-06). Gate
    `@PreAuthorize("@perm.scoped(#uid, 'stockonhand', 'STOCK.ADJUST')")`.
- **uid/id discipline (ADR-0007/0008 D-12):** uids in URLs and request bodies (`productUid`, on-hand `uid`); the
  service resolves them to scalar `Long` ids it persists. The active **company + branch** come from
  `RequestContext`; the create bodies do **not** carry `companyUid`/`branchUid` (the active scope is authoritative
  for an operational, branch-local action — unlike a master create which carries `companyUid`, ADR-0008 D-12). The
  `ApiResponse<T>` envelope everywhere; lists paged via `PageMeta`. Quantities serialise as **strings** (the
  Long-as-string + NUMERIC-as-string discipline — a quantity is `"12.000000"`, never a JS double, to avoid
  precision loss). Enums on the wire as the string name.

### D-12 — Audit (ADR-0004): emit points and `target_type` strings (plural table names)

Stock's **manual** mutating operations emit via `AuditService.record(...)` (MANDATORY, same-TX, append-only —
NFR-STOCK-05). `target_type` strings are the **plural table names** (the shipped V2/V3/V5 convention):

| action | target_type | when | detail (fact-only, ADR-0004 D-6) |
| --- | --- | --- | --- |
| `STOCK.ADJUST` | `stock_movements` | manual ADJUSTMENT posted | `productUid`, `quantity`, `reasonCode`, branch |
| `STOCK.OPENING` | `stock_movements` | manual OPENING_BALANCE posted | `productUid`, `quantity`, branch |
| `STOCK.REORDER.SET` | `stock_on_hand` | reorder level set/cleared | `productUid`, before/after `reorderLevel`, branch |

- **Event-driven movements do NOT emit an `audit_logs` row** (GOODS_RECEIPT, SALE_ISSUE, SALE_REVERSAL,
  GOODS_RECEIPT_REVERSAL). Consistent
  with ADR-0009 D-9 (the outbox does not double-audit) and stock.md §3.1/NFR-STOCK-05: the **business action already
  audits itself** (the sale finalise wrote `SALES.INVOICE.FINALISE`; the Goods Receipt wrote its receive row), the
  **`domain_events` row** records that the event was produced and DISPATCHED, and the **`stock_movements` ledger row
  is itself the immutable audit of the stock effect** (it carries the source event/document, the actor=system, the
  signed quantity, the timestamp). Three append-only trails (business audit, outbox row, movement ledger) — **no
  redundant per-movement `audit_logs` write for system events**. Stated explicitly so no one adds an audit emit to
  the handlers. (The **manual** ops DO audit, above, because they are direct human actions with an actor and need
  the human/security trail.)
- **The movement ledger is the stock audit.** NFR-STOCK-05's "manual operations written to the audit trail" is
  satisfied by the three rows above; "event-driven movements record their originating document/event as their
  reference" is satisfied by `source_event_uid`/`source_document_*` on the movement (D-4).

### D-13 — Permission catalogue additions (seeded in V7, module `stock`)

| code | module | description |
| --- | --- | --- |
| `STOCK.VIEW` | stock | View on-hand levels and movement history |
| `STOCK.ADJUST` | stock | Record a manual stock adjustment (±, reasoned); set a reorder level |
| `STOCK.OPENING` | stock | Seed an opening-balance on-hand for a never-tracked product at a branch |

- **`STOCK.VIEW` + `STOCK.ADJUST` are the two the spec names** (FR-STOCK-15); **`STOCK.OPENING` is split out** for
  opening balances because seeding an initial level is a distinct, typically one-time, higher-trust act than a
  routine count correction (the spec names it as a candidate, FR-STOCK-15). The reorder-level edit folds into
  `STOCK.ADJUST` (it is a stock-control act, not a separate role) — split additively later if the owner wants a
  view-only-with-reorder role.
- **No permission for the event-driven movements** — they are posted by the system consumer under the event's
  authority, not a user action (FR-STOCK-15, ADR-0009 D-9). There is no `STOCK.RECEIVE`/`STOCK.ISSUE` permission;
  the authority is the upstream `SALES.INVOICE.CREATE` / Purchases receive permission that produced the event.
- **Naming** mirrors the shipped catalogue (`PRODUCT.VIEW`/`PRODUCT.MANAGE`, `SALES.INVOICE.*`): dot-separated,
  `MODULE.RESOURCE`/`MODULE.ACTION`.
- **Seeding (V7, idempotent):** `INSERT INTO permissions (code, module, description) VALUES (...) ON CONFLICT (code)
  DO NOTHING`, then the additive `INSERT INTO role_permission SELECT r.id, p.id FROM roles r CROSS JOIN permissions
  p WHERE r.code = 'ORG_ADMIN' AND p.module = 'stock' ON CONFLICT DO NOTHING` — the **exact** V3/V5 pattern.

### D-14 — Migration: additive `V7__stock.sql`, never a V1–V6 edit

IAM=V1, Parties=V2, Products=V3, Units=V4, Sales=V5, **Outbox=V6** (ADR-0009 — built this round, **before** Stock).
Stock is a **new** module → purely **additive `V7__stock.sql`**. It **must not** edit V1–V6. Ordering within V7:

1. **`stock_on_hand`** (D-2) with FKs to `companies`, `branches`, `products`; `uq_stock_on_hand_scope`,
   `uq_stock_on_hand_uid`, `chk_stock_on_hand_reorder`. **No `>= 0` CHECK on quantity** (overselling allowed).
2. **`stock_movements`** (D-4) with FKs to `companies`, `branches`, `products`; `uq_stock_movement_uid`,
   `uq_stock_movement_source_event (source_event_uid, product_id)`, the type / qty / reason CHECKs. **No FK on
   `source_*`** (cross-module scalar references — D-4).
3. **Indexes** (D-2, D-4): `ix_stock_on_hand_company_branch`, `ix_stock_on_hand_product`, the partial
   `ix_stock_on_hand_negative`; `ix_stock_movements_product_branch`, `ix_stock_movements_company_branch`,
   `ix_stock_movements_source_doc`.
4. **Permission seed + additive ORG_ADMIN grant** (D-13).
5. **No `code_sequence` row** (movements have no human number — D-4). **No data seed** (on-hand starts empty;
   levels accrue from the first GOODS_RECEIPT / OPENING_BALANCE). **No trigger** (the on-hand maintenance is the
   service posting primitive, D-4, not a DB trigger — same service-owns-the-invariant stance as the sales totals,
   ADR-0008 D-4). **No FK into `domain_events`/`processed_events`** (V6 platform tables — the link is the
   `source_event_uid` string, not a coupling FK; D-5).

All FK targets (`companies`, `branches`, `products`, `app_users`, `roles`, `permissions`, `role_permission`)
**already exist** in frozen V1/V3. V7 depends on V6 (`domain_events`/`processed_events`) existing as runtime
infrastructure (the handlers write `processed_events`), but takes **no schema FK** into it.

## Consequences

**Easier / safer:**
- **The sale→stock loop is closed, the right way.** A finalised sale's `SALE.FINALISED` event (ADR-0008 D-9, now
  emitted — ADR-0009 D-3) is delivered by the outbox and deducts stock idempotently; a void reverses exactly what
  was issued; a Goods Receipt adds it, and a Goods-Receipt void (`STOCK.RECEIPT.VOIDED`, ADR-0011) reverses exactly
  what was received — the same reverse-from-the-ledger discipline. The ADR-0008 §10 accepted risk ("a v1 sale deducts
  no stock") is **resolved**, and every producer event (Sales finalise/void, GR receive/void) now has a Stock consumer.
- **On-hand is fast and correct.** The maintained `stock_on_hand` row gives an O(1) POS read (NFR-STOCK-08); the
  append-only `stock_movements` ledger is the immutable truth; the same-TX posting primitive (D-4) + the optimistic
  `version` keep them equal (BR-STOCK-01) under concurrency (NFR-STOCK-04), test-pinned (NFR-STOCK-02).
- **Idempotency is two-layered and structural** (NFR-STOCK-03, the release-blocker): the generic `processed_events`
  marker (ADR-0009 D-6a) is the primary dedup, and `uq_stock_movement_source_event (source_event_uid, product_id)`
  (D-4/D-6b) is the inventory-grade DB backstop that correctly handles one-event-many-products (a composed line's
  components). A redelivered event cannot double-move any product.
- **Overselling is a designed, surfaced state, not a bug.** No `>= 0` CHECK; negative on-hand is queryable (partial
  index) and flagged on the DTO; the sale is never blocked (BR-STOCK-03, sales.md FR-SALES-21). The owner's ruling
  is honoured literally.
- **Recipe explosion is single-level, DTO-sourced, decoupled** (D-8) — Stock reads the recipe + stockable facts via
  `ProductService` DTOs; no Products entity import; the composed product is exploded, never deducted (BR-STOCK-04).
- **Quantity-only, valuation not precluded** (BR-STOCK-10, NFR-STOCK-06): no money anywhere; the clean additive
  later change is a nullable `unit_cost`/`Money` on the movement — reserved, not built.
- **Stock stays decoupled** — it implements the `platform.events` handler interface and reads Products DTOs; **no
  module→module entity edge**; two new `ScopeGuard` cases; no new numbering kind. `ModuleBoundaryTest` stays green.
- **TRANSFER is reserved, not built** — the enum values exist (the vocabulary is reserved so the upgrade is
  additive, OQ-STOCK-08) but are excluded from the CHECK, so no transfer row can appear before the feature lands.

**Harder / to watch:**
- **The on-hand == Σ movements invariant is service-owned** (D-4, BR-STOCK-01) — a posting-primitive bug that
  updates one without the other diverges them, which no CHECK catches. **Must have** an integration test that, after
  each operation (receipt, issue, explosion, reversal, adjustment, opening balance), asserts `stock_on_hand.quantity
  == Σ stock_movements.quantity` for the (company, branch, product) (NFR-STOCK-02). Highest-discipline surface.
- **Idempotency is service-owned in the handler** (D-5) — the `processed_events` marker MUST be written in the
  **same TX** as the movement(s) (ADR-0009 D-6 invariant), and the `source_event_uid` MUST be stamped on every
  event-driven movement. **Must have** an integration test that delivers the same `SALE.FINALISED` twice and asserts
  on-hand moves **once** (the round's biggest correctness risk, ADR-0009 Consequences). A second test: a composed
  line redelivered moves each component once (the `(source_event_uid, product_id)` backstop).
- **The system tenant context is a new pattern** (D-5) — the handler runs as the system under the event's
  company/branch, not a request `RequestContext`. The `SystemRequestContext.runAs(...)`-style helper must set AND
  clear correctly (a leaked ThreadLocal across dispatcher iterations would mis-scope the next event). Test the
  set/clear discipline; assert the movement and any audit carry the event's scope with a null actor.
- **Reverse-from-the-ledger for void** (D-5) is the inventory-correct reading of OQ-STOCK-10 but means **both** void
  handlers (`SaleReversalStockHandler` for `SALE.VOIDED`, `GoodsReceiptReversalStockHandler` for `STOCK.RECEIPT.VOIDED`)
  **read** Stock's own ledger (by `source_document_uid`, filtered to the original `SALE_ISSUE` / `GOODS_RECEIPT` rows)
  before posting opposite-sign reversals — a read-then-write under the per-event TX. The unmatched-void anomaly is a
  **log/metric, not a movement** (a zero-effect movement is forbidden); reviewers must not "fix" it by posting a
  phantom movement.
- **The N+1 component read in explosion** (D-8) — reading each component's `ProductDto` for `stockable`. Fine for v1
  (async, small recipes); the recommended additive fix is enriching `ProductComponentDto` with `componentStockable`
  (a Products DTO change, no Stock schema change). Flagged.
- **`source_document_*` are cross-module scalar references with no FK** (D-4) — by design (Stock must not couple to
  `sales_invoices`/`goods_receipts`), but it means a dangling reference is possible if the source doc were ever
  hard-deleted (it is not — sales void is a status, not a delete; receipts are immutable). Documented; do not add an
  FK.
- **`AdjustmentReason` is a service-validated list, not a DB enum-list CHECK** (D-7) — so an out-of-list value is a
  service 422, not a DB violation. Deliberate (the list is owner-tunable); if the owner wants it DB-frozen, add the
  `CHECK (reason_code IN (...))` (flagged).

**Migration / delivery cost:**
- 1 additive Flyway file (`V7__stock.sql`): **2 new tables** (`stock_on_hand`, `stock_movements`), their
  FKs/uniques/CHECKs, **6 indexes** (one partial-on-negative), **3 permission rows + 1 additive ORG_ADMIN grant**.
  **No** `code_sequence` row, **no** data seed, **no** trigger, **no** FK into V6. Depends on frozen V1/V3 (FK
  targets) and runtime V6 (`processed_events`).
- Backend (Stock module): the `stock` entity set (`StockOnHand`, `StockMovement` + DTOs + 2 repositories +
  `StockService`/Impl + `StockPostingService`/Impl + `RecipeExplosionResolver`); the **four `DomainEventHandler`
  beans** (`SaleIssueStockHandler`, `SaleReversalStockHandler`, `GoodsReceiptStockHandler`,
  `GoodsReceiptReversalStockHandler`); the `MovementType`/`AdjustmentReason` enums; the `StockController` (2 manual
  write endpoints + reads). The `ScopeGuard`
  `stockonhand`/`stockmovement` cases (D-10) — adds two repository deps to `ScopeGuard`. A
  `SystemRequestContext.runAs(...)`-style helper in `platform.security` (D-5) for the system-scoped consumer context
  (small, reusable by every future consumer).
- Backend (Products — optional additive, recommended): enrich `ProductComponentDto` with `componentStockable` (+
  base unit) to kill the explosion N+1 (D-8). No schema change; a DTO + projection field. Coordinate with the
  Products owner; non-blocking.
- Backend (cross-round dependency): **ADR-0009's V6 outbox + the four `DomainEventHandler` wiring must be built
  first**, and **Sales must emit `SALE.FINALISED`/`SALE.VOIDED`** (ADR-0009 D-3 closes the ADR-0008 D-9 seam), and
  **Purchases' Goods Receipt must emit `STOCK.RECEIVED`** (ADR-0011). Stock cannot deduct until its producers emit.
- Web: a stock screen — on-hand list/search at the active branch (with negative/low flags), a movement-ledger
  drill-down per product, a manual adjustment form (signed qty + reason dropdown + note), an opening-balance form, a
  reorder-level edit — reusing the Sales/Products list + form patterns. Quantities as strings.
- Deployment risk: **low** — additive migration on frozen schema; on-hand starts empty; the consumers are beans the
  V6 dispatcher discovers by DI. The one sequencing note: **V6 (outbox) + the producers' emit-wiring must ship with
  or before V7**, or events have no consumer / no producer (ADR-0009 D-4's no-handler / no-producer cases apply).

## Alternatives considered

- **Pure-derived on-hand (recompute `SUM(quantity)` from the ledger on every read), no maintained row.** One source
  of truth, no divergence risk. **Rejected (OQ-STOCK-01, owner-ratified D-2):** every POS on-hand read becomes an
  aggregate scan over an append-heavy ledger (NFR-STOCK-08 fails as history grows). The maintained row + same-TX
  posting + test-pinned reconciliation is the boring, fast, correct choice the owner ruled for. (The ledger is
  still the truth; the row is its fast projection.)
- **A maintained row only, no movement ledger** (just increment/decrement on-hand). Simplest, fastest. **Rejected
  (OQ-STOCK-01):** it discards the immutable history (FR-STOCK-05, BR-STOCK-06) — no audit of what moved, no
  reconstruction, no source traceability, no reversal-from-ledger (D-5). The append-only ledger is non-negotiable
  (it is the stock audit, D-12).
- **A DB trigger to maintain on-hand from movement inserts.** Keeps on-hand in lockstep at the DB. **Rejected
  (D-4/D-14):** triggers are the hidden-logic, hard-to-test, owner-disliked mechanism the system avoids (the sales
  totals chose a service calculator over generated columns for the same reason, ADR-0008 D-4). The service posting
  primitive is legible, testable, and the single funnel; the optimistic `version` handles concurrency without a
  trigger.
- **Idempotency by a movement number sequence (`MOV-####`) or by the event uid alone (`UNIQUE (source_event_uid)`).**
  Simpler key. **Rejected (D-4):** a movement has no human number (it is plumbing — no `code_sequence`); and
  `UNIQUE (source_event_uid)` alone **breaks** the legitimate one-event-many-products case (a `SALE.FINALISED` with
  3 lines, or a composed line exploding to 2 components, posts several movements for one event). The
  `(source_event_uid, product_id)` pair is the correct backstop (D-4/D-6b), composed atop the generic
  `processed_events` marker (the primary dedup, ADR-0009 D-6a).
- **A `>= 0` CHECK on `stock_on_hand.quantity` (block overselling at the DB).** Inventory-safe by construction.
  **Rejected (BR-STOCK-03, RATIFIED):** the owner ruled overselling is **allowed** and a SALE_ISSUE that drives
  on-hand negative **must still post** (sales stays stock-agnostic). A `>= 0` CHECK would make the consumer throw on
  an oversell, retry-loop the event, and ultimately FAIL it (ADR-0009 D-4) — blocking the very thing the owner said
  must not block. Negative is a flagged state, not a violation.
- **Storing a `direction` (IN/OUT) column alongside the signed quantity.** Explicit. **Rejected (D-6):** it
  duplicates the `quantity` sign and can drift; direction is derived. The signed quantity is the single source.
- **A separate "skip log" table for non-stockable/skipped lines and unmatched voids.** Structured traceability of
  every nil-effect. **Rejected for v1 (D-9):** the `domain_events` row (DISPATCHED, with payload) + a log/metric
  already record that the event was processed with a nil effect; a movement ledger of *actual* movements stays clean
  (no zero-effect rows). A structured skip-audit table is a future additive option if traceability demands it.
  Reserved, not built.
- **Recursive (multi-level) recipe explosion.** Future-proof for nested BOMs. **Rejected (D-8, FR-PROD-16):**
  Products is single-level; nested BOM is deferred with it (stock.md §12). The resolver explodes exactly one level;
  multi-level lands with the Products nesting ADR.

## Open / flagged items (do NOT block the build; recommended defaults stand)

None changes the `stock_on_hand`/`stock_movements` schema or the consumer/contract semantics; all are tuning,
list-content, or additive-enrichment choices with defaults the design is built to.

1. **`AdjustmentReason` list content (D-7).** Recommended defaults: `COUNT_CORRECTION`, `DAMAGE`, `SHRINKAGE`,
   `EXPIRY`, `RECEIPT_CORRECTION`, `OTHER`. The owner may add/rename before build (a one-edit enum change). **Blocks
   build:** NO — confirm the list before the Stock screen ships.
2. **Freeze the reason list at the DB? (D-7).** v1 validates the value in the service (the CHECK enforces only
   presence-when-ADJUSTMENT), so the list is owner-tunable without a migration. If the owner wants it DB-frozen, add
   `CHECK (reason_code IN (...))`. **Recommended default:** service-validated (tunable). **Blocks build:** NO.
3. **Enrich `ProductComponentDto` with `componentStockable` (+ base unit) to remove the explosion N+1 (D-8).**
   **Recommended default:** do it — it is the cleaner shape and saves a per-component read; it is an additive
   Products DTO field, no Stock schema change. Coordinate with the Products owner. **Blocks build:** NO (the N+1
   works correctly without it).
4. **Reorder-level default-per-product that branches inherit (D-2).** v1 is per-(product, branch), nullable, set
   manually. A product-level default branches inherit is a future additive convenience. **Recommended default:**
   per-(product, branch) only in v1. **Blocks build:** NO.
5. **Reserve a nullable `unit_cost`/`Money` on `stock_movements` now (NFR-STOCK-06)?** **Recommended default:**
   do NOT add it in v1 (quantity-only is ratified; an unused money column invites the assumption Stock knows value).
   When valuation lands (Finance-aware round), it is a clean additive ALTER on the movement. **Blocks build:** NO.
6. **`STOCK.OPENING` as a distinct permission vs folding into `STOCK.ADJUST` (D-13).** Recommended: keep it distinct
   (opening-balance seeding is a higher-trust, one-time act). If the owner prefers one permission, drop `STOCK.OPENING`
   and gate opening balances on `STOCK.ADJUST` — a seed change before build. **Blocks build:** NO.

## Summary

This ADR specifies the Stock data model as **two tables** in `com.erp.modules.stock`: a maintained **`stock_on_hand`**
level (one **signed** `NUMERIC(19,6)` quantity per `(company, branch, product)` via `uq_stock_on_hand_scope`, an
optional indicator-only `reorder_level`, an optimistic `version`, **no `>= 0` CHECK** because overselling is allowed
and flagged) and an append-only **`stock_movements`** ledger (signed `quantity`, `movement_type` ∈
{GOODS_RECEIPT, SALE_ISSUE, SALE_REVERSAL, GOODS_RECEIPT_REVERSAL, ADJUSTMENT, OPENING_BALANCE} with TRANSFER
reserved-not-CHECKed,
`source_event_uid` + `source_document_*` provenance, `reason_code` mandatory-for-ADJUSTMENT, **no money column**,
**no `updated_*`**). On-hand is maintained from movements in the **same transaction** via a single
`StockPostingService.post(...)` primitive under the optimistic `version` (BR-STOCK-01, NFR-STOCK-02/04). Stock is the
**first transactional-outbox consumer**: four `platform.events.DomainEventHandler` beans —
**`SaleIssueStockHandler`** (`SALE.FINALISED` → SALE_ISSUE, with **single-level recipe explosion** reading the
Products recipe + stockable facts **via DTO**, non-stockable components skipped-and-recorded),
**`SaleReversalStockHandler`** (`SALE.VOIDED` → SALE_REVERSAL, **reversing only what the ledger shows was issued**,
recording an anomaly if nothing matches — OQ-STOCK-10), **`GoodsReceiptStockHandler`** (`STOCK.RECEIVED` →
GOODS_RECEIPT), and **`GoodsReceiptReversalStockHandler`** (`STOCK.RECEIPT.VOIDED` → GOODS_RECEIPT_REVERSAL, the
buying-side mirror of the sale reversal — **reversing only the GOODS_RECEIPT rows the ledger shows were received**
for that receipt, anomaly-if-no-match, deduping on the void event's own uid) — each acting **as the system under the
event's tenant scope**, idempotent via the generic
**`processed_events`** marker (ADR-0009 D-6a, primary) **and** the inventory-grade
**`uq_stock_movement_source_event (source_event_uid, product_id)`** backstop (ADR-0009 D-6b, defined here — keyed by
the pair so one event legitimately moves many products without double-applying any). Manual **adjustment** and
**opening-balance** endpoints are `@perm`-gated (`STOCK.ADJUST` / `STOCK.OPENING`, with `STOCK.VIEW` for reads), take
**branch from `RequestContext`** (not the body), assert `stockable` via Products DTO, and are audited (manual ops
emit `audit_logs`; event-driven movements do **not** — the business action, the `domain_events` row, and the movement
ledger are the three trails). The enforcement split is the established DB-can't / service-must (DB CHECKs for
type/qty-non-zero/reason-presence/reorder; service for stockable, same-company, on-hand==Σmovements, idempotency,
explosion). The migration is a single additive **`V7__stock.sql`** (two tables, six indexes, three permissions + an
ORG_ADMIN grant, **no `code_sequence`, no seed, no trigger, no FK into V6**) that never edits V1–V6. No ADR-blocking
question remains — every flagged item is a list-content / tuning / additive-enrichment choice with a recommended
default the design is built to. **This ADR consumes ADR-0009's outbox, depends on ADR-0009 (V6) and the Sales/Purchases
emit-wiring shipping first, and closes the sale→stock loop ADR-0008 §10 left open: a finalised sale now deducts
stock, idempotently, in base units, with recipe explosion, and a void reverses exactly what was issued. Ready for
build.**
