Verified against the **shipped** [V1__baseline.sql](../../backend/src/main/resources/db/migration/V1__baseline.sql) / [V3__products.sql](../../backend/src/main/resources/db/migration/V3__products.sql) (the `code_sequence` shape) / [V5__sales.sql](../../backend/src/main/resources/db/migration/V5__sales.sql) (table style — `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `uid VARCHAR(26)`, plural tables, singular constraint roots `uq_`/`fk_`/`chk_`, plural index names `ix_`, audit cols, `JSONB` for `tax_summary`) — the SQL is ground truth; the prose naming doc was stale. **Confirmed: no `domain_event(s)` table, no `com.erp.platform.events` classes exist yet** — this is greenfield platform infrastructure, latest migration is V5 → outbox is **`V6__domain_events.sql`** (additive; never edit V1–V5).

This ADR is the **technical design** for the transactional-outbox platform infrastructure. It translates the ratified Stock/Purchases requirement ("the cross-module link is the transactional outbox; build it this round; at-least-once + consumer-side idempotency dedupe on event id") and the reserved ARCHITECTURE.md §9 / ADR-0008 D-9 shape into a table, a producer API, a poller/dispatcher, a consumer contract, and the failure/ordering/idempotency semantics — **concrete enough that the backend engineer builds `V6__domain_events.sql` + the `platform.events` classes without guessing**. It does **not** write production code or the migration — that is the engineer's next step. It is the **foundation** ADR-0010 (Stock) and ADR-0011 (Purchases) build on, and it **closes the ADR-0008 D-9 seam** (Sales will call `outbox.publish(...)` on finalise/void).

## Context

Every cross-module effect the system has reserved — Sales→Stock deduction, Purchases→Stock receipt, and the compensating reversals — has the **same shape**: a business transaction in module A must reliably cause an effect in module B, **without A calling into B's services** (that would break `ModuleBoundaryTest` and couple their transactions). ARCHITECTURE.md §9 already **named** the answer (a `domain_event` row written in the same TX, dispatched by a poller; never in-memory `ApplicationEventPublisher`); ADR-0008 D-9 **reserved** the first two event types and their payload and deliberately **did not build** the table (no consumer existed). This round, **Stock is the first consumer** and Purchases the second producer, so the owner ruled (OQ-STOCK-09 = YES) the outbox is **built now, as platform infrastructure, under this ADR** — not folded into the Stock or Purchases data-model ADRs (it is cross-cutting plumbing, not a module table).

The central forces:

- **Atomicity is the whole point — the event must be written in the SAME transaction as the business change.** A `SALE.FINALISED` event must be persisted iff the sale finalised; a `STOCK.RECEIVED` iff the Goods Receipt received. If the event write and the business write could diverge (two systems, two commits), a sale could finalise without ever deducting stock, or stock could deduct for a sale that rolled back. The outbox pattern exists precisely to make the event a **row in the same database, committed in the same TX** as the business aggregate. This is why an in-memory `ApplicationEventPublisher` (events lost on crash before dispatch) and a direct broker publish (commits independently of the DB TX) are both **wrong** here — ARCHITECTURE.md §9 already ruled them out. The publisher API must therefore enrol in the **caller's** transaction, not open its own.

- **No message broker — single-container QA, simple deploy.** The system is a modular monolith on one Spring Boot container against one PostgreSQL (ARCHITECTURE.md §1). There is no Kafka/Rabbit and adding one is a deployment and operational burden the owner has not asked for and the scale does not need. The dispatcher is therefore an **in-process `@Scheduled` poller** that reads PENDING rows and invokes **in-process consumers** (Stock's handler is a bean in the same JVM). This is the boring option PROJECT-CONVENTIONS demands; a broker is a future scaling ADR, not now.

- **At-least-once delivery → consumers MUST be idempotent (owner-ratified).** A polled outbox cannot give exactly-once delivery cheaply: a crash between "consumer succeeded" and "row marked DISPATCHED" redelivers the event. The owner ratified **at-least-once + consumer-side idempotency, dedupe on event id** (OQ-STOCK-09, FR-STOCK-13, BR-STOCK-08, BR-PURCH-06). The outbox guarantees *delivery* (the event is never lost); the *consumer* guarantees *effect-once* (a redelivered event posts no second stock movement). The design must make consumer idempotency cheap and the default.

- **A poison event must not block the queue.** If one event's consumer throws repeatedly (a bug, bad data), the poller must retry it a bounded number of times and then **park it (FAILED) and move on** — a single bad row must never stall `SALE.FINALISED` events for every other sale. Ordering is therefore **best-effort by `occurred_at`**, not a strict global FIFO that one stuck row can wedge.

- **Compensation is the consumer's job, not the outbox's.** `SALE.VOIDED` reverses `SALE.FINALISED`; a GR void reverses `STOCK.RECEIVED`. The outbox just delivers the compensating event in order; the *reversal logic* (post a `SALE_REVERSAL`, reverse only what was issued — OQ-STOCK-10) lives in the Stock consumer. The outbox is a delivery channel, not a saga orchestrator.

- **Build lean for QA; make scaling additive.** QA runs **one container**, so a single poller cannot double-dispatch (there is only one). The design must be **correct and simple under one instance**, and must make the multi-instance upgrade (`SELECT … FOR UPDATE SKIP LOCKED`, the same row-lock discipline `code_sequence` already uses, ADR-0007 D-6) a **drop-in additive change** — not a redesign. Do not build distributed-locking machinery no one is running yet.

- **Schema freeze / migration ordering.** IAM=V1, Parties=V2, Products=V3, Units=V4, Sales=V5 — all frozen and shipped. The outbox is a **new** platform table landing as a purely **additive `V6__domain_events.sql`**; it must not edit V1–V5. It depends only on `companies`/`branches` (frozen V1) for its scope FKs.

## Decision

### D-1 — Package placement: `com.erp.platform.events` (cross-cutting infrastructure, owned by no business module)

The outbox lives entirely under the **already-carved-out** `com.erp.platform.events` package (ARCHITECTURE.md §2 reserved it: "domain-event outbox (`domain_event`) + dispatcher (later modules)"). It is **platform infrastructure**, not a business module — it has **no `com.erp.api` controller, no REST surface, no permission** (D-9). Indicative layout:

```
com.erp.platform.events
├── DomainEvent                 (entity — the domain_events row; extends the UidEntity shape)
├── DomainEventStatus           (enum: PENDING | DISPATCHED | FAILED)
├── DomainEventRepository       (Spring Data; the poller's claim query + idempotency lookups)
├── OutboxPublisher             (interface) + OutboxPublisherImpl
│                               (the producer API — D-3; serialises payload → JSONB,
│                                inserts a PENDING row in the CALLER's transaction)
├── DomainEventHandler          (interface — the consumer contract, D-5; keyed by event type)
├── DomainEventDispatcher       (the @Scheduled poller, D-4; claims PENDING, invokes handlers,
│                                marks DISPATCHED / increments attempt + records last_error)
├── ProcessedEvent              (entity — the consumer-side dedup marker, D-6) [optional table, D-6]
├── ProcessedEventRepository
└── DomainEventType             (canonical event-type + aggregate-type String constants, D-3)
```

> **Boundary note for `ModuleBoundaryTest`:** `platform.events` is **cross-cutting** — like `platform.security` (`ScopeGuard`, `RequestContext`), `platform.audit` (`AuditService`), and `platform.common` (`Money`, `ApiResponse`), it is a platform primitive that business modules **depend on**, never the reverse. **Producers** (`sales`, `purchases`) depend on the `OutboxPublisher` interface in `platform.events`; **consumers** (`stock`) implement the `DomainEventHandler` interface from `platform.events` and register their bean. **Producers and consumers never depend on each other** — Sales does not import anything from Stock; it publishes a `SALE.FINALISED` row and is done. The dispatcher discovers handlers by Spring DI (all `DomainEventHandler` beans injected), so the wiring is by interface, not by cross-module import. The events the publisher carries are **plain data** (event-type string + a JSONB payload of scalars and uids), not another module's entity — the same DTO-only / scalar-id discipline `agents.app_user_id` and the Sales→Products reads already use. `platform.events` must be on the `ModuleBoundaryTest` allow-list as a platform package modules may import (alongside `platform.security`/`audit`/`common`); **no module→module edge is created** — that is the rule this design protects.

### D-2 — The `domain_events` table (plural) — `V6__domain_events.sql`

A single append-only outbox table. **Plural `domain_events`** per the shipped convention (masters/event-logs are plural — `audit_logs`, `sales_invoices`, `tax_rates`; junctions are singular). This **reconciles** the stale singular `domain_event` name in ARCHITECTURE.md §9 / ADR-0008 D-9: those reserved the *shape*, written before the plural-table convention was settled in shipped SQL (the [db-naming-convention] note records that the prose was stale and the SQL is ground truth). The shipped name is **`domain_events`**; ARCHITECTURE.md §9 is updated to match (a one-word doc edit, noted in Consequences).

The table carries **`company_id` + `branch_id`** (the originating tenant scope, copied from the producing aggregate) — but it is a **platform infrastructure table, not a tenant-predicated business table**: the poller reads it **un-scoped** (it dispatches every company's events; the dispatcher runs as the system, not a request — there is no `RequestContext`). The scope columns are carried so the consumer can **set the tenant context from the event** when it posts its effect (the Stock movement is written under the event's `company_id`/`branch_id`, not a logged-in user's — stock.md §4 "System (event consumer) acts under the originating event's company/branch context"). `branch_id` is **NULLable** — most events are branch-scoped (a sale/receipt is at one branch), but the design does not force a branch onto an event that has none; the three v1 events all carry a branch, so in practice it is always set, but the column does not constrain a future company-level event.

#### `domain_events`

| column | type | null? | notes |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | NO | internal key; the **event id** the consumer dedupes on (D-6) |
| `uid` | `VARCHAR(26)` | NO | ULID; `uq_domain_event_uid`; the **stable external event identifier** carried in the payload envelope and used as the consumer dedup key (uid-not-id discipline, §3.3) |
| `event_type` | `VARCHAR(60)` | NO | canonical type string, `MODULE.EVENT` form: `SALE.FINALISED`, `SALE.VOIDED`, `STOCK.RECEIVED` (D-3); the dispatch routing key |
| `aggregate_type` | `VARCHAR(40)` | NO | the producing aggregate kind, e.g. `SALES_INVOICE`, `GOODS_RECEIPT` (for diagnostics/replay grouping) |
| `aggregate_id` | `BIGINT` | NO | the producing aggregate's internal `id` (e.g. `sales_invoices.id`) — **no FK** (cross-module; the outbox must not FK into a business table it does not own — same scalar-reference discipline as `audit_logs`) |
| `aggregate_uid` | `VARCHAR(26)` | NO | the producing aggregate's `uid` (e.g. the invoice uid) — the **stable** external reference the payload echoes; what the consumer records as the movement's source reference |
| `company_id` | `BIGINT` | NO | FK → `companies(id)`; originating tenant scope (set from the aggregate; the consumer posts its effect under this company) |
| `branch_id` | `BIGINT` | **YES** | FK → `branches(id)`; originating branch (set from the aggregate); NULLable for a future company-level event — all v1 events set it |
| `payload` | `JSONB` | NO | the event body (D-3); for `SALE.FINALISED`: `{ invoiceUid, companyId, branchId, finalisedAt, lines:[{ productId, productUid, unitId, qtyInBase }] }` (ADR-0008 D-9, verbatim). `JSONB` matches the shipped `audit_logs.detail` / `sales_invoices.tax_summary` usage |
| `status` | `VARCHAR(20)` | NO | `PENDING` \| `DISPATCHED` \| `FAILED`; DEFAULT `'PENDING'`; CHECK below; the poller's work-queue state (D-4) |
| `occurred_at` | `TIMESTAMPTZ` | NO | DEFAULT `now()`; when the business event happened (= the finalise/receive time, in the producing TX); the **poller's ordering key** (oldest-first) |
| `dispatched_at` | `TIMESTAMPTZ` | YES | set when `status → DISPATCHED` (all handlers succeeded); NULL while PENDING/FAILED |
| `attempt_count` | `INTEGER` | NO | DEFAULT 0; incremented on each delivery attempt that fails (D-4); the retry/cap counter |
| `last_error` | `VARCHAR(1000)` | YES | the last failure's message (truncated, user-safe — no stack trace, no secrets); NULL until a failure; diagnostic for FAILED rows |
| `version` | `BIGINT` | NO | DEFAULT 0; optimistic lock — guards the single-instance claim→update race and is the seam the multi-instance `SKIP LOCKED` upgrade slots into (D-4) |

> **No standard `created_by`/`updated_by` audit columns.** Unlike business tables, an outbox row has no human author — it is written by the producing service inside a TX and mutated only by the system dispatcher. `occurred_at` (write time) + `dispatched_at` + `attempt_count` + `last_error` are its lifecycle. `created_at` is redundant with `occurred_at` and omitted. This is deliberate: the outbox is plumbing, the **business action already audits itself** (the finalise/receive writes its own `audit_logs` row — ADR-0004, ADR-0008 D-13) (D-9).

**Constraints on `domain_events`:**
- `uq_domain_event_uid UNIQUE (uid)`.
- `fk_domain_event_company FOREIGN KEY (company_id) REFERENCES companies (id)`.
- `fk_domain_event_branch  FOREIGN KEY (branch_id)  REFERENCES branches (id)` (NULLable column; FK still enforced when present).
- `chk_domain_event_status CHECK (status IN ('PENDING','DISPATCHED','FAILED'))`.
- `chk_domain_event_attempt CHECK (attempt_count >= 0)`.
- **No FK on `aggregate_id`** — by design (cross-module scalar reference; the outbox does not own and must not couple to `sales_invoices`/`goods_receipts`).

**Indexes (the poller's claim query is the hot path):**
```
-- THE poller index: claim PENDING events oldest-first (status filter + occurred_at order).
-- Partial on status='PENDING' keeps the index tiny as DISPATCHED rows accumulate (the working set
-- is only undispatched rows); expression/partial index is the shipped Postgres-native discipline.
CREATE INDEX ix_domain_events_pending
    ON domain_events (occurred_at)
    WHERE status = 'PENDING';

-- FAILED triage / dead-letter review.
CREATE INDEX ix_domain_events_failed
    ON domain_events (occurred_at)
    WHERE status = 'FAILED';

-- Replay / diagnostics by aggregate (e.g. "all events for this invoice").
CREATE INDEX ix_domain_events_aggregate
    ON domain_events (aggregate_type, aggregate_id);

-- Tenant-scoped diagnostics.
CREATE INDEX ix_domain_events_company
    ON domain_events (company_id);
```

The **partial index on `status = 'PENDING'`** is the key performance decision: the outbox is append-heavy and most rows quickly become `DISPATCHED`, so a full index on `status` would bloat; a partial index over only the undispatched working set stays small and makes the poller's "oldest PENDING first" query an index-only range scan no matter how many million DISPATCHED rows have accumulated.

### D-3 — The producer API: `OutboxPublisher`, called inside the business transaction; canonical type constants in `platform.events`

Producers (`sales`, `purchases`) publish through a single small platform interface, called **inside their own `@Transactional` service method** so the event row commits atomically with the business change:

```
public interface OutboxPublisher {
    /** Inserts a PENDING domain_events row in the CALLER's current transaction.
     *  payload is serialised to JSONB. Returns the new event's uid. */
    String publish(String eventType,
                   String aggregateType,
                   Long   aggregateId,
                   String aggregateUid,
                   Long   companyId,
                   Long   branchId,      // nullable
                   Object payload);      // serialised to JSONB by the impl (Jackson)
}
```

- **Same-transaction guarantee.** `OutboxPublisherImpl` does a plain `repository.save(new DomainEvent(...))` with **no `@Transactional(propagation=REQUIRES_NEW)`** — it **must enrol in the caller's transaction** so the event is committed iff the business change is. (`SalesInvoiceServiceImpl.finalise` is already `@Transactional`; `publish` runs within it.) If the finalise rolls back, the event row rolls back with it. **This is the atomicity invariant — the engineer must not give `publish` its own transaction.**
- **Payload serialisation.** The impl serialises the `payload` POJO to `JSONB` via Jackson (the same `ObjectMapper` the API uses, so `Money`/uid serialisation is consistent). The producer hands a typed record (e.g. a `SaleFinalisedPayload` record owned by the producing module's `domain.dto`, or a generic map) — the publisher only needs `Object`.
- **Canonical event-type + aggregate-type constants live in `platform.events.DomainEventType`** (a constants holder), **not** scattered as string literals in each producer:
  ```
  // event types (MODULE.EVENT)
  SALE_FINALISED  = "SALE.FINALISED"
  SALE_VOIDED     = "SALE.VOIDED"
  STOCK_RECEIVED  = "STOCK.RECEIVED"
  // aggregate types
  AGG_SALES_INVOICE = "SALES_INVOICE"
  AGG_GOODS_RECEIPT = "GOODS_RECEIPT"
  ```
  Both producer and consumer reference the **same constant**, so a typo cannot silently misroute an event. These constants are the **contract**; the canonical payload shapes are owned alongside (the `SALE.FINALISED` / `SALE.VOIDED` payload is fixed by ADR-0008 D-9, the `STOCK.RECEIVED` payload is fixed by ADR-0011/purchases.md FR-PURCH-08 mirroring it). New event types are added here under their owning module's ADR.
- **Closing the ADR-0008 D-9 seam (this is the headline consumer-facing change to Sales).** `SalesInvoiceServiceImpl.finalise` replaces its `// TODO(stock): emit SALE.FINALISED outbox event — ADR-0008 D-9` seam with a call to `outbox.publish(DomainEventType.SALE_FINALISED, AGG_SALES_INVOICE, invoice.getId(), invoice.getUid(), invoice.getCompanyId(), invoice.getBranchId(), payload)` **inside the finalise TX**; `void` emits `SALE.VOIDED` likewise. This is a **localised service addition** (a publisher dependency + two `publish` calls) — exactly what ADR-0008 D-9 designed for; no Sales schema change, no Sales contract change. Specified here, executed under the Sales-wiring work this round.

### D-4 — The dispatcher: a `@Scheduled` in-process poller, oldest-first, retry-with-cap, FAILED-and-skip

A single `DomainEventDispatcher` bean polls and dispatches:

- **Schedule.** A `@Scheduled(fixedDelayString = "${erp.outbox.poll-interval-ms:1000}")` method (configurable; ~1s default for QA — near-real-time stock effects without busy-spinning). `fixedDelay` (not `fixedRate`) so a slow batch never overlaps itself under one instance.
- **Claim + dispatch loop (single-instance, QA — the built behaviour):**
  1. Read a **bounded batch** of PENDING rows **oldest-first** by `occurred_at` (e.g. `findTop100ByStatusOrderByOccurredAtAsc('PENDING')`, hitting `ix_domain_events_pending`), where `attempt_count < ${erp.outbox.max-attempts:5}`.
  2. For each event, in its **own per-event transaction** (so one event's success commits independently of the next — a later poison event does not roll back already-applied ones):
     - resolve **all** `DomainEventHandler` beans whose `eventType()` matches `event.event_type` (D-5);
     - invoke each handler with the event (the consumer sets tenant context from the event's `company_id`/`branch_id`, dedupes on `event.uid`, and applies its effect — D-5/D-6);
     - on **all handlers succeeding** → set `status = 'DISPATCHED'`, `dispatched_at = now()`;
     - on **any handler throwing** → `attempt_count += 1`, `last_error = <message>`, leave `status = 'PENDING'` (so it is retried next poll) **until** `attempt_count` reaches `max-attempts`, then set `status = 'FAILED'` (parked — D-failure).
  3. A **FAILED event is skipped** by the claim query (it filters `attempt_count < max-attempts` / `status = 'PENDING'`), so **a poison event never blocks the events behind it** — the loop moves to the next row.
- **No event with zero matching handlers is an error in v1** — if no consumer is registered for an `event_type` (e.g. Sales emits `SALE.FINALISED` in a deployment where Stock is absent), the dispatcher marks it `DISPATCHED` (delivered to the registered set, which is empty) and logs at DEBUG. *(This matters during the build window: Sales can be wired to emit before the Stock consumer lands, and events do not pile up as PENDING forever — but see the flagged item; the conservative alternative is to leave them PENDING until a handler exists. Recommended default: mark DISPATCHED when no handler is registered, because in this round Stock ships **with** the producers, so a no-handler event is a misconfiguration to surface, not a normal state.)*
- **Single-instance safety (QA = one container).** With exactly one poller there is no concurrent claim, so a plain "read PENDING, process, update" loop **cannot double-dispatch** — there is only one reader. The `version` optimistic lock on the row is belt-and-braces (and the hook the multi-instance upgrade needs). **This is the built behaviour; it is correct for QA's single container.**
- **Multi-instance upgrade is additive, not a redesign (D-scaling).** When the system scales to >1 container, two pollers must not both claim the same row. The drop-in change is to make the claim query a `SELECT … FOR UPDATE SKIP LOCKED LIMIT n` (native query on the repository) so each poller claims a **disjoint** batch — the **identical row-lock discipline `code_sequence` already uses** for concurrency-safe numbering (ADR-0007 D-6), the boring Postgres-native answer. This is a **one-method change** (swap the finder for a `@Query(nativeQuery=true)` `... FOR UPDATE SKIP LOCKED`), gated behind the same `version`/claim seam — **no table change, no consumer change**. Built **only when** multi-instance deploy is real (flagged, non-blocking); QA does not need it.

### D-5 — The consumer contract: `DomainEventHandler` keyed by event type, registered by Spring DI

Consumers implement a single platform interface; the dispatcher discovers them by injection (no central registry to maintain):

```
public interface DomainEventHandler {
    /** the event_type this handler consumes (a DomainEventType constant). */
    String eventType();
    /** apply the effect. MUST be idempotent (D-6): a redelivered event posts no second effect.
     *  Runs within the dispatcher's per-event transaction; throw to signal failure (→ retry). */
    void handle(DomainEvent event);
}
```

- **Routing.** The dispatcher injects `List<DomainEventHandler>` and groups by `eventType()`; for each event it invokes every handler whose `eventType()` equals the event's `event_type`. A `STOCK.RECEIVED` event reaches Stock's `GoodsReceiptStockHandler`; a `SALE.FINALISED` reaches Stock's `SaleIssueStockHandler` (which does recipe explosion, stock.md FR-STOCK-08); a `SALE.VOIDED` reaches Stock's `SaleReversalStockHandler`. **All three v1 consumers live in `com.erp.modules.stock`** and implement this `platform.events` interface — that is the only cross-cutting coupling (D-1 boundary note).
- **Tenant context from the event.** A handler runs as the **system**, not a request — there is no JWT, no `RequestContext` branch. The handler sets the working company/branch **from the event's `company_id`/`branch_id`** before writing its movement (stock.md §4). ADR-0010 (Stock) specifies how the Stock consumer establishes this context (a system-scoped context, distinct from the request-scoped `RequestContext`); this ADR fixes only that the **event carries the scope** the consumer must use.
- **The handler's `handle` is invoked inside the dispatcher's per-event transaction**, so the consumer's effect (the stock movement + on-hand update + the dedup marker, D-6) and the event's `DISPATCHED` mark commit together — the consumer's idempotency marker is written in the **same TX** that applies the effect, which is what makes "apply-once" atomic with "mark-processed" (D-6).

### D-6 — Consumer-side idempotency: a `processed_events` marker per (consumer, event uid); Stock's recommended approach

At-least-once delivery means a handler may see the same event twice; **the consumer must dedupe** (FR-STOCK-13, BR-STOCK-08, NFR-STOCK-03 — the single biggest correctness risk, a release blocker if violated). Two viable mechanisms; the design provides a **generic marker** and Stock **also** has a natural key — use both layers:

**(a) The generic dedup marker — `processed_events` table (platform-provided, recommended primary mechanism):**

A tiny platform table the consumer writes **in the same TX as its effect**:

| column | type | null? | notes |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | NO | |
| `consumer` | `VARCHAR(80)` | NO | the handler's logical name (e.g. `STOCK.SALE_ISSUE`) — so two consumers of the same event each dedupe independently |
| `event_uid` | `VARCHAR(26)` | NO | the `domain_events.uid` processed |
| `processed_at` | `TIMESTAMPTZ` | NO | DEFAULT `now()` |

- `uq_processed_event UNIQUE (consumer, event_uid)` — the dedup key. The handler, at the **start** of `handle`, attempts to record `(consumer, event.uid)`; if it already exists (or the insert hits the unique constraint), the event is a **redelivery → the handler returns without applying the effect** (idempotent no-op). Because the marker insert and the effect (the stock movement) are in the **same per-event TX** (D-5), they commit together: either both happen (first delivery) or the marker already exists (redelivery → skip). A crash *after* the effect but *before* the event row is marked DISPATCHED redelivers the event → the marker insert now collides → no double-movement. **This is the mechanism that satisfies NFR-STOCK-03.**
- `consumer`-keyed (not just `event_uid`) so a future second consumer of `SALE.FINALISED` dedupes on its own progress, independently.
- Indexes: the unique constraint indexes the lookup; no other index needed (it is keyed-access only).

**(b) The consumer's own natural idempotency (Stock — a defence-in-depth layer):** Stock's `stock_movements` ledger can additionally carry the **source event uid** (`source_event_uid`) with a **partial unique constraint per (movement source, event uid)**, so even absent the marker a second `SALE_ISSUE` from the same event uid is rejected by the DB. This is **ADR-0010's** call (the movement table is Stock's); recorded here as the **recommended belt-and-braces** so the Stock movement is self-evidently traceable to its originating event and the dedup is enforced at the inventory grade. The OQ-STOCK-10 reconciliation (a `SALE.VOIDED` for a sale never issued → reverse only what was issued, else record an anomaly) is the Stock handler reading its own ledger by `source_event_uid` — which (b) makes a keyed lookup.

**Recommendation:** ship **`processed_events` (a)** as the generic, reusable platform mechanism (every future consumer gets idempotency for free), **and** have Stock additionally stamp `source_event_uid` on its movement rows **(b)** for inventory-grade traceability and a DB-level backstop. (a) is in **V6** (platform, this ADR); (b) is in **V7/Stock** (ADR-0010). A consumer that has a strong natural idempotency key may rely on (b) alone, but (a) is the default the platform provides so no consumer has to reinvent it.

### D-7 — Ordering & failure semantics

- **Ordering is best-effort by `occurred_at`, oldest-first** (the poller's `ORDER BY occurred_at` + the partial index, D-2/D-4). This gives **per-aggregate causal order in practice** (a `SALE.FINALISED` is published before its `SALE.VOIDED` — earlier `occurred_at` — so the issue is dispatched before the reversal). It is **not** a strict global total order and does not need to be: consumers are idempotent (D-6) and the only ordering that matters is per-aggregate (finalise-before-void), which `occurred_at` preserves because both events for one aggregate are produced by serialised business transactions on that aggregate. **Out-of-order edge** (a `SALE.VOIDED` consumed before its `SALE.FINALISED` — e.g. clock skew, or a void racing a slow first poll) is handled by the **consumer** per OQ-STOCK-10: reverse only what was actually issued (looked up by `source_event_uid`, D-6b); if nothing matches, **record an anomaly** for review rather than posting a phantom negative movement. The outbox does not attempt to reorder; the consumer reconciles.
- **A poison event does not block the queue** (D-4): a repeatedly-failing event is retried up to `max-attempts` then parked `FAILED`; the claim query skips FAILED and `attempt_count`-exhausted rows, so events behind it keep flowing. One bad `SALE.FINALISED` cannot stop stock deductions for every other sale.
- **Compensation is the consumer's responsibility, not the outbox's.** The outbox delivers `SALE.VOIDED` / the GR-void event in order; the **reversal logic** (post a `SALE_REVERSAL` in-movement reversing the prior `SALE_ISSUE`(s), including a composed product's component issues — stock.md FR-STOCK-12) lives in the Stock consumer (ADR-0010). The outbox is a delivery channel; it is **not** a saga coordinator and holds no compensation state.
- **Retry is at the whole-event grain.** If an event has multiple handlers and one fails, the event stays PENDING and **all** its handlers are re-invoked next poll — which is exactly why **every handler must be idempotent** (D-6): a re-invoked already-succeeded handler must no-op. (v1 has one handler per event type, so this is theoretical now, but the contract is stated so a future second handler is safe.)

### D-8 — Failure handling: retry cap, FAILED parking, dead-letter is a read, not a table

- **Retry with cap.** `attempt_count` increments on each failed delivery; at `${erp.outbox.max-attempts:5}` the event is parked `FAILED` (D-4). A transient failure (a brief DB hiccup, a momentary consumer error) self-heals on the next poll; a persistent one stops retrying after the cap so it does not burn the poller forever.
- **`FAILED` rows ARE the dead-letter queue** — no separate `domain_events_dead_letter` table in v1. A FAILED row retains its full payload, `attempt_count`, and `last_error`; the `ix_domain_events_failed` index makes "show me the parked events" a cheap query. **Operational recovery** is a manual/operational action: fix the cause, then reset `status='PENDING', attempt_count=0` to replay (a small platform admin path or a direct DB action — flagged, not built in v1; QA has none). A dedicated dead-letter table is a future additive change if FAILED volume ever warrants it; the boring option (FAILED is a status, the row stays) is correct for now.
- **No retry backoff in v1** — fixed `poll-interval-ms` is the de-facto delay between attempts (~1s). An exponential backoff (a `next_attempt_at` column the claim query honours) is an additive enhancement if a flapping consumer ever makes tight retries costly; not needed for QA (flagged).

### D-9 — Permission & audit: the outbox is internal plumbing — no API, no permission, and it does NOT emit audit

- **No REST surface, no permission code.** The outbox has **no controller** and **no IAM permission** (it is not a user-facing resource; nothing in `com.erp.api` touches it). Producers call it from within their already-permissioned service methods (the finalise that publishes `SALE.FINALISED` is gated by `SALES.INVOICE.CREATE` — ADR-0008 D-11; the publish is a side effect of an already-authorised action). The dispatcher runs as the system on a schedule, under no user.
- **The outbox does NOT write `audit_logs`.** It is **plumbing**, and the **business action already audits itself**: the finalise writes its own `SALES.INVOICE.FINALISE` audit row (ADR-0008 D-13), the void its `SALES.INVOICE.VOID` row, the Goods Receipt its receive/void rows (purchases.md NFR-PURCH-03). Auditing the event emission too would double-log the same business fact with no added security value — the human/security trail is the business audit; the **outbox's own append-only history IS its audit** (the `domain_events` row, its `attempt_count`/`dispatched_at`/`last_error`, and the consumer's `processed_events` marker together are a complete, queryable record of what was produced, delivered, and processed). The **stock movement ledger** the consumer writes is itself the audit of the stock effect (stock.md §3.1, NFR-STOCK-05). So: business action audits (ADR-0004 aspect/service), the outbox row records delivery, the movement ledger records effect — three append-only trails, **no redundant outbox audit**. Stated explicitly so no one adds an audit emit to the dispatcher.

### D-10 — Migration: additive `V6__domain_events.sql`, never a V1–V5 edit; uid discipline

IAM=V1, Parties=V2, Products=V3, Units=V4, Sales=V5 — all frozen and shipped. The outbox is a **new** platform table → purely **additive `V6__domain_events.sql`**. It **must not** edit V1–V5. Ordering within V6:

1. **`domain_events`** table (D-2) with FKs to `companies` and (nullable) `branches`; the status / attempt CHECKs.
2. **`processed_events`** table (D-6a) with its `uq_processed_event (consumer, event_uid)`.
3. **Indexes** (D-2): the partial `ix_domain_events_pending` (the poller hot path), `ix_domain_events_failed`, `ix_domain_events_aggregate`, `ix_domain_events_company`.
4. **No permission seed** (D-9 — the outbox has no permission). **No `code_sequence` row** (the outbox uses ULID `uid`s, not a per-company human number). **No data seed** (the table starts empty; events accrue at runtime).

All FK targets (`companies`, `branches`) exist in frozen **V1** — no dependency on un-frozen schema. **uid discipline (§3.3):** every `domain_events` row carries a ULID `uid` (the external event identifier, the consumer dedup key, what the payload envelope echoes); the `id` is the internal key; the payload references other aggregates by **uid** (`invoiceUid`, `productUid`) not raw id, matching the ADR-0008 D-9 contract and the uid-in-payload discipline. Table style follows shipped V5 exactly: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `uid VARCHAR(26)`, plural table name, singular constraint roots (`uq_domain_event_*`, `fk_domain_event_*`, `chk_domain_event_*`, `uq_processed_event`), plural index names (`ix_domain_events_*`), `JSONB` for `payload`.

> **Doc reconciliation (non-blocking):** ARCHITECTURE.md §9 and ADR-0008 D-9 name the table `domain_event` (singular). The shipped plural-table convention makes it **`domain_events`**; ARCHITECTURE.md §9 will be updated to the plural name and to reference this ADR as the built design (a one-line doc edit). ADR-0008 D-9 stays as written (it reserved the *shape* and is now *closed* by this ADR — the column set it sketched is honoured, with `aggregate_uid`/`attempt_count`/`last_error`/`version` added as this ADR specifies).

## Consequences

**Easier / safer:**
- **Reliable cross-module effects from day one, the right way.** A sale finalising or a Goods Receipt receiving writes its event in the **same TX** as the business change (D-3), so the effect can never be silently lost (the in-memory `ApplicationEventPublisher` failure mode ARCHITECTURE.md §9 forbids is structurally impossible) nor fire for a rolled-back transaction. Stock deductions/receipts are guaranteed-delivered, idempotently applied.
- **Modules stay decoupled.** Sales and Purchases depend only on the `OutboxPublisher` interface; Stock implements `DomainEventHandler`; **no module→module edge** (D-1). `ModuleBoundaryTest` stays green — `platform.events` is a platform primitive like `security`/`audit`/`common`, on the allow-list, consumed by modules, depending on none.
- **Idempotency is the platform default.** `processed_events` (D-6a) gives every current and future consumer at-least-once-safe dedup for free, written in the same TX as the effect — NFR-STOCK-03 (the round's biggest correctness risk) is structurally addressed, not hoped for. Stock's `source_event_uid` (D-6b) adds an inventory-grade DB backstop and the OQ-STOCK-10 reconciliation lookup.
- **Lean for QA, scalable later without a redesign.** One `@Scheduled` poller, correct under one container (D-4); the multi-instance upgrade is a **one-method swap** to `FOR UPDATE SKIP LOCKED` (the `code_sequence` discipline already shipped, ADR-0007 D-6) — no table change, no consumer change (D-scaling). No broker to operate.
- **A poison event cannot wedge the queue** (D-4/D-7): retry-with-cap, park FAILED, skip — one bad event never stops the others. FAILED rows are a queryable dead-letter (D-8) with full payload + `last_error` for triage.
- **Closes the ADR-0008 D-9 seam cleanly** (D-3): the reserved `// TODO(stock)` becomes two `outbox.publish` calls in the finalise/void TX — a localised service addition, no Sales schema/contract change. The reserved payload is honoured verbatim.
- **The foundation ADR-0010 (Stock) and ADR-0011 (Purchases) build on.** Stock's consumers, Purchases' `STOCK.RECEIVED` producer, and Sales' wiring all reference this one mechanism — they specify *what* flows; this ADR fixed *how* it flows.

**Harder / to watch:**
- **Consumer idempotency is a service-owned invariant** (D-6) — the dedup marker must be written **in the same TX** as the effect; getting that wrong (marker in a separate TX, or after the effect commits) reopens the double-movement risk. **Must have** an integration test that delivers the same event twice and asserts on-hand moves once (NFR-STOCK-03) — the highest-discipline surface in this work, owned by ADR-0010's tests.
- **Same-TX publish is a service-owned invariant** (D-3) — `OutboxPublisher.publish` must **not** open its own transaction; if an engineer adds `REQUIRES_NEW` the atomicity guarantee breaks (event commits even if the business TX rolls back). An integration test must assert: roll back the finalise → no `domain_events` row.
- **Ordering is best-effort, not strict** (D-7) — correctness rests on consumer idempotency + per-aggregate `occurred_at` order + the OQ-STOCK-10 reconciliation, **not** on a guaranteed global FIFO. Reviewers must not assume strict ordering; the consumer handles the out-of-order edge.
- **The single-instance assumption is load-bearing for QA** (D-4) — the plain poll loop is safe **only** under one container. Deploying a second container **without** first applying the `SKIP LOCKED` upgrade would double-dispatch (mitigated by consumer idempotency, but it would burn double work). The multi-instance flag (below) must be honoured before scaling out.
- **No-handler events** (D-4) — the recommended default (mark DISPATCHED when no handler is registered) means an event with a mistyped `event_type`, or emitted in a deployment missing its consumer, is silently "delivered" to nobody. Mitigated because Stock ships **with** the producers this round; a DEBUG log surfaces it; the conservative alternative (leave PENDING) is flagged.
- **FAILED-event recovery is operational, not automated** (D-8) — replaying a parked event is a manual reset in v1 (no admin UI). Acceptable for QA; a recovery path is flagged for production.

**Migration / delivery cost:**
- 1 additive Flyway file (`V6__domain_events.sql`): **2 new tables** (`domain_events`, `processed_events`), their FKs/uniques/CHECKs, **4 indexes** (one partial-on-PENDING — the hot path), **no** permission seed, **no** `code_sequence` row, **no** data seed, **no** trigger. Depends only on frozen V1 (`companies`/`branches`).
- Backend (platform): the `platform.events` set — `DomainEvent` entity + `DomainEventStatus` enum + `DomainEventRepository` (the claim finder), `OutboxPublisher`(+Impl), `DomainEventHandler` interface, `DomainEventDispatcher` (the `@Scheduled` poller), `DomainEventType` constants, `ProcessedEvent` entity + repo. Config keys `erp.outbox.poll-interval-ms` / `erp.outbox.max-attempts`. ArchUnit allow-list entry for `platform.events`.
- Backend (Sales wiring — closes ADR-0008 D-9): an `OutboxPublisher` dependency on `SalesInvoiceServiceImpl` + two `publish` calls (finalise → `SALE.FINALISED`, void → `SALE.VOIDED`) replacing the `// TODO(stock)` seam; a `SaleFinalisedPayload`/`SaleVoidedPayload` record in `sales.domain.dto`. **No Sales schema or contract change.**
- Backend (consumers — ADR-0010/Stock): Stock's `DomainEventHandler` beans (`SALE.FINALISED` → issue + recipe explosion, `SALE.VOIDED` → reversal, `STOCK.RECEIVED` → receipt), each writing `processed_events` + its movement + `source_event_uid` in one TX. (Specified in ADR-0010, not here.)
- Backend (producer — ADR-0011/Purchases): the Goods Receipt's `outbox.publish(STOCK.RECEIVED, ...)` on receive + compensating event on void. (Specified in ADR-0011, not here.)
- Web: **none** — the outbox has no UI (D-9). (A FAILED-event admin view is a future, optional operational screen.)
- Deployment risk: **low** — additive migration on frozen schema; the table starts empty; the poller is a single scheduled bean with bounded batches; no broker to provision. The one operational note: **do not run more than one container until the `SKIP LOCKED` upgrade is applied** (D-4/flagged).

## Alternatives considered

- **Spring in-memory `ApplicationEventPublisher` (`@TransactionalEventListener`) instead of a persisted outbox.** Zero new table, native Spring. **Rejected (and already forbidden by ARCHITECTURE.md §9):** an in-memory event is **lost if the process crashes after commit but before the listener runs** — a sale would finalise with no stock deduction and no record that the deduction was owed. The whole reason the requirement names a *transactional outbox* (a persisted row in the same TX) is to survive a crash and be redelivered. The in-memory publisher cannot give at-least-once delivery (OQ-STOCK-09). It is the exact anti-pattern the convention rules out.
- **A real message broker (Kafka / RabbitMQ) with the outbox as a CDC/relay source.** The textbook large-scale outbox. **Rejected for v1:** there is no broker in the stack, QA is a single container, and the deploy is deliberately simple (ARCHITECTURE.md §1). A broker adds infrastructure to provision, secure, and operate for a monolith whose consumers run **in the same JVM** — solving a distribution problem the system does not have. The in-process polled dispatcher is the boring, sufficient choice; a broker is a future scaling ADR if the monolith ever splits, and the persisted `domain_events` table is already the correct *source* for a future relay (so this is not a dead end).
- **`REQUIRES_NEW` transaction for `publish` (write the event in its own committed TX).** Would guarantee the event row survives even if the business TX later rolls back. **Rejected (D-3) — it is the bug, not the feature:** the event must commit **iff** the business change commits. A separately-committed event for a rolled-back finalise would deduct stock for a sale that never happened. `publish` **must** enrol in the caller's TX. Stated as an explicit invariant because it is an easy mistake.
- **Strict global FIFO ordering (single-row-at-a-time, never skip a failed event).** Simplest ordering story. **Rejected (D-7):** one poison event would block **every** subsequent event indefinitely (no stock effects for any sale until the bad one is fixed) — an availability failure. Best-effort `occurred_at` order + idempotent consumers + retry-cap-then-skip gives the only ordering that matters (per-aggregate finalise-before-void) without letting one bad row wedge the queue.
- **No generic dedup table — rely solely on each consumer's natural idempotency** (e.g. Stock's `source_event_uid` alone, D-6b). Fewer tables. **Rejected as the default (D-6):** it makes every future consumer reinvent idempotency, and a consumer without an obvious natural key has nothing. The generic `processed_events` marker gives every consumer correct at-least-once dedup for free, in the same TX as the effect; Stock *also* keeps its natural key as defence-in-depth. Provide both; default to the generic.
- **Build the dispatcher with `FOR UPDATE SKIP LOCKED` (multi-instance-safe) now.** Most future-proof. **Rejected for the v1 build (D-4/D-scaling):** QA runs one container, where a plain poll loop cannot double-dispatch; `SKIP LOCKED` solves a concurrency problem no one has yet. It is a documented **one-method additive upgrade** (the same `code_sequence` row-lock discipline) for when multi-instance deploy is real — building it now is speculative machinery the "prefer the boring option" stance rejects. Reserved, not built.
- **A separate `domain_events_dead_letter` table for FAILED events.** Cleaner separation of parked events. **Rejected for v1 (D-8):** `FAILED` is a status; the row stays put with its payload + `last_error`, and a partial index makes parked events a cheap query. A dedicated table adds a move-on-failure step and a second schema for no v1 benefit (QA has no FAILED-volume problem). Additive later if warranted.

## Open / flagged items (do NOT block the build; recommended defaults stand)

1. **Multi-instance dispatcher (`SELECT … FOR UPDATE SKIP LOCKED`).** Built behaviour is single-instance-safe (D-4); the multi-instance upgrade is a one-method additive change. **Recommended default:** ship single-instance for QA; apply the `SKIP LOCKED` upgrade **before** running more than one container. **Blocks build:** NO. (Operational gate: do not scale out the API without this.)
2. **Retry backoff (`next_attempt_at` / exponential).** v1 retries every poll interval up to the cap (D-8). **Recommended default:** fixed-interval retry; add a `next_attempt_at` column (additive) only if a flapping consumer makes tight retries costly. **Blocks build:** NO.
3. **Dead-letter recovery path (replay a FAILED event).** v1 recovery is a manual `status='PENDING', attempt_count=0` reset (D-8); no admin UI. **Recommended default:** operational/manual for QA; a small platform admin endpoint + screen for production (its own minor ADR/permission when needed). **Blocks build:** NO.
4. **No-handler event policy (D-4).** **Recommended default:** mark DISPATCHED + DEBUG-log when no handler is registered (Stock ships with the producers this round, so a no-handler event is a misconfiguration to surface). The conservative alternative (leave PENDING) is available if the owner prefers events to wait for a future consumer. **Blocks build:** NO.
5. **Poll interval (`erp.outbox.poll-interval-ms`) and `max-attempts`.** **Recommended defaults:** 1000 ms poll, 5 attempts. Tunable config, no schema change. **Blocks build:** NO.
6. **Old DISPATCHED-row retention / archival.** `domain_events` is append-only and will grow; the partial-on-PENDING index keeps the poller fast regardless, but the table itself grows unbounded. **Recommended default:** leave all rows in v1 (they are a replay/audit asset; volume is trivial at QA scale); add a periodic archival/purge of old DISPATCHED rows (e.g. >90 days) as an operational job if size ever matters. **Blocks build:** NO.

None of the above changes the `domain_events` / `processed_events` schema or the producer/consumer contracts; all are tuning, operational, or additive-upgrade choices with defaults the design is built to.

## Summary

This ADR builds the **transactional outbox** as platform infrastructure in `com.erp.platform.events`: a single append-only **`domain_events`** table (plural, reconciling the stale singular name in ARCHITECTURE.md §9 / ADR-0008 D-9) carrying `id`, ULID `uid`, `event_type`, `aggregate_type`/`aggregate_id`/`aggregate_uid`, `company_id`/nullable `branch_id`, `JSONB payload`, `status` (PENDING/DISPATCHED/FAILED), `occurred_at`/`dispatched_at`, `attempt_count`/`last_error`/`version`, with a **partial index on `status='PENDING'`** as the poller's hot path; a small **`OutboxPublisher`** producers call **inside their own transaction** (so the event commits iff the business change does — the atomicity invariant), with canonical type constants (`SALE.FINALISED`, `SALE.VOIDED`, `STOCK.RECEIVED`) in `platform.events.DomainEventType`; a **`@Scheduled` in-process poller** that claims PENDING events oldest-first, invokes registered **`DomainEventHandler`** beans, marks DISPATCHED on success and retries-with-cap-then-FAILED-and-skips on failure (a poison event never blocks the queue); **at-least-once delivery with consumer-side idempotency** via a generic **`processed_events`** marker per `(consumer, event_uid)` written in the same TX as the effect (Stock additionally stamps `source_event_uid` on its movements as a DB backstop and the OQ-STOCK-10 reconciliation key); **best-effort `occurred_at` ordering** with compensation owned by the consumer (`SALE.VOIDED` → `SALE_REVERSAL`), **no API/permission**, and **no outbox audit** (the business action and the movement ledger already audit). It is built **lean for the single-container QA** (correct under one poller) with the multi-instance `SELECT … FOR UPDATE SKIP LOCKED` upgrade reserved as a one-method additive change (the shipped `code_sequence` row-lock discipline). The migration is a single additive **`V6__domain_events.sql`** (two tables, four indexes, no seed) that never edits V1–V5. **This is the foundation ADR-0010 (Stock — the first consumer) and ADR-0011 (Purchases — the second producer) build on, and it closes the ADR-0008 D-9 seam: Sales will call `outbox.publish` on finalise (`SALE.FINALISED`) and void (`SALE.VOIDED`) inside the finalise/void transaction.** No ADR-blocking question remains; every flagged item is a tuning/operational/additive-upgrade choice with a recommended default the design is built to, and the one cross-module guarantee (atomic same-TX publish + idempotent consumption) is placed deliberately and test-pinned.
