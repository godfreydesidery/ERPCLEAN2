# 0042 — POS API gap closure: idempotency, reversal, multi-tender, field clarity (minimum-modification plan)

- **Status:** Proposed (implementation plan — NO production code changed by this ADR)
- **Date:** 2026-06-19
- **Deciders:** solutions-architect (with backend-engineer for the implementation shapes)
- **Context source:** [docs/integration/pos/12-known-limitations.md](../integration/pos/12-known-limitations.md) (the 4 POS API gaps, code-grounded); [ADR-0029](0029-sales-depth.md) (POS — `PosSaleController`, `PosSaleServiceImpl`, sessions, drawer reconcile, `POS_VARIANCE`/`POS_CASH_OVER`/`POS_CASH_SHORT`); [ADR-0013](0013-general-ledger-data-model.md) (the cash-sale GL entry); [ADR-0009](0009-transactional-outbox.md) (`SALE.VOIDED`/`SALE.FINALISED` events + `processed_events` idempotency pattern); ADR-0041 D3 (`AddPaymentRequest` structured tender-instrument refs — already shipped). Verified against the shipped code (file:line cited inline).

## Context

The POS limitations doc lists four API gaps. This ADR is the **minimum-modification** plan to close them. The guiding principle (owner directive): **add the smallest possible API surface — reuse existing capabilities rather than build new subsystems.**

The key finding from reading the code is that **most of the machinery already exists**; the POS endpoint simply does not use it:

- **Invoice void with full reversal exists** — `voidInvoice` ([SalesInvoiceServiceImpl.java:377](../../backend/src/main/java/com/erp/modules/sales/service/SalesInvoiceServiceImpl.java#L377)), endpoint `PUT /api/v1/sales-invoices/uid/{uid}/void` ([SalesInvoiceController.java:85](../../backend/src/main/java/com/erp/api/SalesInvoiceController.java#L85)), FINALISED-only, emits `SALE.VOIDED` → GL reversal (`SaleVoidingHandler`) + stock reversal (`SaleReversalStockHandler`); works on POS/DIRECT origin.
- **The payment layer is already multi-tender** — `addPayment` ([SalesInvoiceServiceImpl.java:565](../../backend/src/main/java/com/erp/modules/sales/service/SalesInvoiceServiceImpl.java#L565)) accepts every `TenderType` (CASH/MOBILE_MONEY/CHEQUE/CARD), is callable repeatedly on a draft, and **ADR-0041 D3 already added** `cashBankAccountId`/`chequeId`/`mobileMoneyRef`/`cardRef` to `AddPaymentRequest`. The POS orchestrator hard-codes one CASH payment ([PosSaleServiceImpl.java:125](../../backend/src/main/java/com/erp/modules/sales/service/PosSaleServiceImpl.java#L125)).
- **No request-level idempotency exists** — `X-Request-Id` is logging/correlation only ([JwtRequestContextFilter.java:74](../../backend/src/main/java/com/erp/platform/security/JwtRequestContextFilter.java#L74)). This is the single genuinely-new (but small) capability.

### Hardening classification (answering "which require API hardening")

| # | Gap | Hardening? | Why |
|---|---|---|---|
| 1 | Idempotency | **YES — true hardening** | The only new integrity guard; prevents double-posting. |
| 2 | Reversal/refund | Integrity gap, **engine already exists** | Reuse `voidInvoice`; real work is RBAC exposure + the POS-drawer rule. |
| 3 | Multi-tender | **No core hardening** | Payment layer already hardened (ADR-0041); this is feature exposure. |
| 4 | Ignored fields | **No** | API clarity only — relax validators + fix Javadoc. |

## Decision

### D-1 — Idempotency on `POST /pos/sales` (the one true hardening item; do first)

**Approach: an `Idempotency-Key` HTTP header — NO change to `PosSaleRequest`.** This is the minimum-modification form of a real integrity fix: the request body is untouched.

- The client generates one opaque key per **logical sale attempt** and resends the *same* key on a retry of an ambiguous outcome.
- New table (one small table; mirrors the outbox `processed_events` shape):
  ```
  pos_sale_idempotency
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PK
    company_id    BIGINT      NOT NULL  FK companies(id)
    idem_key      VARCHAR(80) NOT NULL            -- the client header value
    request_hash  VARCHAR(64)                     -- optional: sha-256 of the body, to detect key reuse with a different payload
    invoice_uid   VARCHAR(26)                     -- the result (the created invoice); NULL only mid-flight
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
    CONSTRAINT uq_pos_idem UNIQUE (company_id, idem_key)
  ```
- **Flow (insert-marker-in-the-same-TX, the `IdempotencyGuard` pattern):** in the sale's transaction, attempt to insert `(company_id, idem_key)`. On unique-constraint conflict → the sale already ran: load `invoice_uid`, return the original `SalesInvoiceDto` (HTTP `200`, or `201` with the original body). On success → process the sale, stamp `invoice_uid`, commit. A concurrent duplicate is serialised by the unique constraint (the second blocks, then sees the committed row → returns the original).
- **Optional `request_hash`:** reject (`422`) a reused key with a *different* body — surfaces a client bug rather than silently returning the wrong invoice.
- **Scope:** per company (the `Idempotency-Key` is company-scoped via the authenticated principal). Retention: purge rows older than N days (operational, additive).
- **Surface added:** one header + one table. `PosSaleRequest` unchanged.

> Reuse note: this is the same "unique marker written in the same TX as the effect" mechanism the outbox already uses for consumer idempotency — we are extending the pattern to the request edge, not inventing one.

### D-2 — POS reversal: reuse `voidInvoice`; the cash leg is already handled

**Approach: a thin `POST /api/v1/pos/sales/uid/{uid}/reverse` that delegates to the existing `voidInvoice`.** Zero new reversal logic.

```
POST /api/v1/pos/sales/uid/{uid}/reverse   body: { "reason": "<text>" }
@PreAuthorize("@perm.scoped(#uid,'invoice','POS.SALE.VOID')")
-> salesInvoiceService.voidInvoice(uid, new VoidInvoiceRequest(reason));   // existing
```

**Cash-leg analysis (the crux — and it is already correct).** A POS sale is a **cash sale**, so `SalesPostingHandler` posts a single SALES journal **`DR Cash / CR Revenue / CR VAT`** ([SalesPostingHandler.java:26](../../backend/src/main/java/com/erp/modules/gl/events/SalesPostingHandler.java#L26)) — there is **no AR leg**. `voidInvoice` emits `SALE.VOIDED` → `SaleVoidingHandler` posts a `SALES_REVERSAL` of the *whole* SALES entry ([SaleVoidingHandler.java:95](../../backend/src/main/java/com/erp/modules/gl/events/SaleVoidingHandler.java#L95)), i.e. **`DR Revenue / DR VAT / CR Cash`**. The cash is reversed *because it lives in the SALES journal*. **There is no dangling cash leg in the GL** — the earlier worry (an AR/cash mismatch) does not apply to the cash-sale model.

**What #2 actually has to get right is the POS DRAWER, not the GL:**

1. **The session's expected-cash must exclude VOID sales.** Reconcile computes `expected = openingFloat + cashSalesTotal − payouts` ([PosSessionServiceImpl.java:137](../../backend/src/main/java/com/erp/modules/sales/service/PosSessionServiceImpl.java#L137)). `computeCashSalesTotal(session)` **must filter out `status = VOID`** so a voided sale lowers expected cash (matching the physical cash the cashier hands back). **Verify/ensure this filter exists** — it is the one behavioural check this gap turns on.
2. **Do NOT also record a `payout(REFUND)` for a voided sale.** That would double-subtract (the void already removes the sale from `cashSalesTotal`). The reversal is the single accounting act; `pos_session_payouts` stays for genuine non-sale cash-out only.
3. **Session-state rule.** Allow the POS reverse only while the originating session is **OPEN** (the drawer can absorb the refund). A sale in a **CLOSED/RECONCILED** session is a back-office correction: still permitted via the invoice void, but the cash difference is then a reconciled-variance matter, not a till refund. State this explicitly so the client knows.
4. **Scope:** v1 reverses the **whole** POS invoice (`voidInvoice` is all-or-nothing). **Partial / line-level refunds are deferred** (they need a credit-note-by-line path — out of scope here).

**Permission:** add `POS.SALE.VOID` (or `POS.SALE.REFUND`) to `R__seed_permissions.sql` + the ORG_ADMIN grant (the convergent-seed path from ADR-0009-consolidation). Alternatively reuse `SALES.INVOICE.VOID` with no new code — but a POS-scoped code keeps cashier RBAC clean.

**Surface added:** one controller method + one permission. No new service/GL/stock code.

### D-3 — Multi-tender: loop the existing `addPayment`

**Approach: an OPTIONAL `tenders` list on `PosSaleRequest`; iterate the existing `addPayment`.** Backward compatible.

- Add to `PosSaleRequest` (additive, nullable):
  ```
  List<PosTender> tenders        // optional; if null/empty -> today's single exact-CASH behaviour
  PosTender = { TenderType tenderType, BigDecimal amount, String currency?,
                Long cashBankAccountId?, Long chequeId?, String mobileMoneyRef?, String cardRef? }
  ```
- In `PosSaleServiceImpl`, replace the single hard-coded `addPayment(... CASH, grossTotal ...)` with a loop:
  ```
  for (t : tenders) invoiceService.addPayment(invoiceUid,
      new AddPaymentRequest(t.tenderType, t.amount, currency, t.reference,
                            t.cashBankAccountId, t.chequeId, t.mobileMoneyRef, t.cardRef));
  ```
  (The 9-arg `AddPaymentRequest` already exists — ADR-0041 D3.)
- **Validation:** `sum(tenders.amount) ≥ grossTotal`; change (over-tender) only on CASH per BR-SALES-07 (already in the payment/`change_amount` layer — confirm it is applied on the POS finalise path); each tender's currency matches the header (BR-CUR-07, already enforced in `addPayment`).
- **Backward compatibility:** absent `tenders` ⇒ exactly today's behaviour. No existing client breaks.
- **Surface added:** one optional list field + its element record. Zero new payment infrastructure.

> Note: once `tenders` exists, `tenderedAmount` (today "receipt only") is redundant for CASH change — change is derivable from the CASH tender vs gross. Keep it for now; flag for removal in D-4.

### D-4 — Required-but-ignored fields: clarity, not hardening (smallest change)

- **`LineItem.unitPrice`** — server-authoritative pricing is **correct and safe**; keep it. Remove the misleading `@NotNull @DecimalMin` (make the field nullable/ignored) and **fix the Javadoc** (it currently claims "validated against list price" — it is *ignored*). Negotiated reductions already go through `lineDiscountAmount`. *(Optional, MORE surface — not recommended for v1:* honour `unitPrice` as a permission-gated `POS.SALE.PRICE_OVERRIDE`, audited, mirroring the back-office `overrideLinePrice`.)*
- **`agentId`** — today `@NotNull` but ignored (the orchestrator passes `null`, so the recorded agent is always the cashier — [PosSaleServiceImpl.java:94](../../backend/src/main/java/com/erp/modules/sales/service/PosSaleServiceImpl.java#L94)). Two minimal options:
  - **(a) Forward it** (recommended): resolve `agentId → agentUid` and pass it into the `CreateSalesInvoiceRequest` agent slot. A few lines; makes the required field meaningful. *Behaviour change to flag:* the recorded agent becomes the submitted one, not always the cashier.
  - **(b) Drop the `@NotNull`** if POS sales are intentionally always the cashier.
- **Classification:** API clarity. No integrity hardening. Backward compatible (clients may still send the fields).

## Minimum-modification summary

Net new API surface across all four gaps:

- **1 header** (`Idempotency-Key`, #1)
- **1 optional endpoint** (`POST /pos/sales/uid/{uid}/reverse`, #2) — delegates to existing void
- **1 optional list field** (`tenders`, #3) — loops existing `addPayment`
- **2 relaxed validators + Javadoc fixes** (#4)
- **2 small tables/seed**: `pos_sale_idempotency` table (#1), one `POS.SALE.VOID` permission (#2)

Everything else is **reuse** of shipped capabilities (void, the multi-tender payment layer, the `processed_events` idempotency pattern).

## Recommended sequence

1. **D-1 idempotency** — the only true hardening; header-only; highest data-integrity value. Build first.
2. **D-2 reversal** — reuse `voidInvoice`; deliver the endpoint + permission, and **verify the `computeCashSalesTotal` excludes VOID** + set the OPEN-session rule.
3. **D-3 multi-tender** — additive `tenders` list + orchestrator loop; backward compatible.
4. **D-4 clarity** — relax validators, fix Javadoc, forward `agentId`.

## Consequences / what to verify before/while implementing

- **#1:** the response (created `invoice_uid`) MUST be stored on the marker so a replay returns the *same* invoice; handle the concurrent in-flight duplicate (unique constraint serialises it); decide key retention/purge.
- **#2:** confirm `computeCashSalesTotal` filters `status != VOID` (else expected-cash is wrong); do **not** double-account with a payout; document the closed/reconciled-session policy; partial refunds deferred; confirm a paid-in-full POS invoice remains `FINALISED` (it does — cash sale posts no AR open item, so no settlement status change) so `voidInvoice`'s FINALISED-only guard passes.
- **#3:** confirm the over-tender/`change_amount` (BR-SALES-07) path is exercised on the POS finalise; per-tender currency match.
- **#4:** relaxing the validators is backward compatible; **forwarding `agentId` changes recorded behaviour** — call it out in the integration guide; once `tenders` lands, retire `tenderedAmount`.

## Status of this document

This is a **plan only** — no production code, DTO, migration, or endpoint has been changed by this ADR. The shapes above (table DDL, endpoint, DTO fields) are the proposed designs for the implementation step, sized for minimum API modification.
