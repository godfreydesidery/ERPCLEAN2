## The Executive Report Suite

### 1. The principle

An operational report lists transactions; an executive report answers a question. Every screen in this suite states one number, carries the comparison that makes it mean something (same weekday, last year, budget, or the branch next door), and ends in a decision the owner can take with his thumb — approve, hold, call, order a count. If a figure has no comparison it is noise, and if it has no available action it belongs in the web client, not on the phone.

Three rules follow from that, and they constrain every row below:

- **Six numbers above the fold, every number a tap.** Full tables are export-only.
- **Every margin figure carries a coverage badge.** Sales lines hold no cost in this schema — `sales_invoice_lines` has no cost column at all (verified: `V5__sales.sql`). Cost is reconstructed from the stock ledger by a *separate* query keyed on `stock_movements.movement_type = 'SALE_ISSUE'` joined to the invoice uid, and the shipped code comments say it plainly: *"Unmatched lines (unvalued/service/kit) contribute 0 — margin then equals net"*, and a `SALE_ISSUE` row can carry a NULL `value_amount`, which is coalesced to zero. Both paths compute as **100% margin**. Any aggregate that hides that will be discovered, and it will discredit the whole app. The badge ("margin computed on 94% of sales value") is one line of UI and it is non-negotiable.
- **Stale but stamped beats a spinner.** Every screen caches its last payload with an "as at 06:14" mark. This is Tanzania on mobile data, in a car.

A fourth rule, forced by verification: **every gate in this suite is written `@PreAuthorize("@perm.has('CODE')")`** — that is the shipped idiom across all ~140 controllers, not Spring's `hasPermission`. Uid-addressed operations use `@perm.scoped(#uid,'<type>','CODE')`, which additionally resolves the target's company and runs it through `ScopeGuard`.

It needs no schema change.

### 3. The full catalogue

Permission codes are marked **(seeded)** only where the grounding pass found them in `R__seed_permissions.sql`. **Every `EXEC.*` code is new — a grep of the seed file returns exactly zero `EXEC.` matches (verified: 0 of 252 seeded codes).** A gated-but-unseeded code passes CI, works for root, and breaks for every real executive user; each must be added in the same change as its endpoint, and tested as a **non-root** user.

Status key: **READY** = usable as-is · **RESHAPE** = endpoint exists, needs a mobile DTO/params · **BUILD** = new endpoint over existing data · **BLOCKED** = data does not exist (named).

### 4. Alerts, not reports

A report waits to be opened; an alert interrupts a person. Different product, different failure mode: a noisy report is ignored, a noisy alert gets **muted** — and a muted channel is worse than none, because everyone believes they are covered.

Six rules, enforced in the sender rather than hoped for in the thresholds: one named recipient role resolved by permission (never "all managers") · a shipped default threshold with a per-company override · a deduplication window · a one-tap action · an auto-resolve when the condition reverses · **a hard budget of three non-critical pushes per person per day**, the excess rolling into the 07:30 digest.

**Lock-screen text carries no money.** A TZS figure on a lock screen in a shared car is a data breach; the number lives behind the tap.

|---|---|---|---|---|

### 5. The consolidation question

**True multi-company consolidation is not possible today, and it is not primarily a reporting problem.** Stated plainly, because softening this would set the owner up to quote a wrong number to a bank. All four points below were re-verified against the shipped code, and all four hold.

1. **The read path forbids it.** `ScopeGuard.canActIn` (`backend/src/main/java/com/erp/platform/security/ScopeGuard.java`) ends, literally:
   `return principal.root() || companyId.equals(principal.companyId());`
   A non-root user — which every real executive is — can read **exactly one company per request**: their active one. Moving between companies is done by switching branch via `X-Branch-Uid`, and `JwtRequestContextFilter` requires a **live, unrevoked, active** `user_branch` assignment for a non-root caller before it rebuilds the principal on that branch's company. There is no organisation-scoped read path and no `X-Company-Uid` (verified: neither string appears in the codebase). This is the larger half of the problem and it is architectural, not analytical.
   *One nuance the draft omitted, and it is good news for plumbing only:* ADR-0062 put a tenant check **above** that line and made it apply to root, and the principal now carries `organisationId`, with a `CompanyTenantIndex.organisationOf(companyId)` already in the security path. The organisation is therefore already a first-class runtime concept — an org-scoped read path has a foothold to build on. It changes nothing about points 2–4.
2. **Eliminations are impossible.** There is no intercompany marker anywhere — not on `journal_lines`, not on AR/AP documents, not as an account convention. A summed group P&L **double-counts every inter-entity sale**, which in a distribution group is routinely 20–40% of revenue, with nothing in the data that could detect it.
3. **There is no currency translation.** `companies.base_currency` is per company (V10). `journal_lines` carry `debit_amount`/`credit_amount`/`currency` and **no base column at all**. `currency_rates.rate_type` does admit `('SPOT','CLOSING','AVERAGE','BUDGET')` — but the only consumer found is the FX revaluation run, which records which rate type it used; **no closing/average translation logic exists**, and there is no translation reserve. Adding two companies with different base currencies is not conservative — it is arithmetically meaningless.
4. **There is no group chart of accounts** (`chart_of_accounts` is company-scoped; `parent_id` is present with an FK and the comment "*reserved for later grouping; NULL in v1*") and **fiscal calendars are per company** (`fiscal_years` / `fiscal_periods` are company-scoped), so "YTD" is not comparable across entities without a mapping and a calendar-window rule.

**What "consolidated" honestly means in v1:** a **per-company comparative view** — one column per company, each with its own close-status trust score in the header, and a *combined* total only where every company shares one base currency. It carries a permanent, non-dismissible banner: **"Combined total of legal entities. Intercompany transactions are NOT eliminated."** Where base currencies differ, the code must **refuse to render a total** rather than add TZS to USD. That per-company comparative delivers most of the value the owner is actually asking for, and it is honest.

**What proper consolidation would take** — four separate pieces of work, each an owner decision before any code:
- an **organisation-scoped read path** with its own permission (`EXEC.GROUP.VIEW`, new) and a deliberate tenant predicate — designed, not bolted onto an existing endpoint;
- an **intercompany counterparty tag** on AR/AP documents plus an IC account convention **[schema]**;
- a **group account mapping** (many local accounts → one group reporting line) **[schema]**;
- a **translation layer** (closing rate for balance-sheet items, period-average for P&L, with a translation reserve) — the rate types already exist in `currency_rates` and no translation logic consumes them.

Recommendation: ship the per-company comparative in wave 1, and treat true consolidation as its own project with its own approval.

### 7. Build order

**The rule for wave 1:** a report earns a place if (a) it needs **no schema change and no new entity**, (b) it answers a question the owner asks **at least weekly**, and (c) it ends in an action he can take from the phone. Everything else waits — with one deliberate exception, below.

**The one exception, and it must be decided before wave 1 starts.** Every trend, every same-weekday comparison, every turns and dead-stock band, every ABC class and every league table requires replaying 12–24 months of sales lines and stock movements. There is no fact or snapshot table in the schema, and the finest reporting grain shipped anywhere is the **fiscal period** — the BI trends literally iterate `FiscalPeriodRepository`. Live computation on a phone over Tanzanian mobile data will not reach a usable first paint, and an app that feels slow will not be opened twice regardless of how good the reports are. The recommendation is a nightly-materialised `exec_daily_fact` at (company, branch, business date) — carrying sales, COGS, gross profit, **uncosted sales value and line count** (so the coverage badge costs nothing at read time), collections, stock value, AR, AP, cash, adjustment value and till variance — refreshed by a scheduled job, plus one covering index on the stock-movement side of the margin reconstruction, created `CONCURRENTLY` in its own non-transactional migration. **That is [schema] and needs the DDL and version presented for approval before anything is authored.** Wave 1 below is sequenced so that the reports which do not need it come first.

**Wave 1 — the reason to install the app.** Daily habit forms here or not at all.
Morning Brief · Exceptions queue · Approvals with decision context (approve/reject already works, and every latency timestamp is already stored) · Cash position and commitments · EFD failed-receipts list · AR ageing with credit risk · Company-wide AP ageing with commitments and GRNI · Shrinkage and adjustment-by-user · Discount and override leakage · Till integrity · Van reconciliation (already an endpoint and a seeded permission) · Purchase price variance (already computed, never readable) · Close status and trust score · the alert set that needs no new type (approvals, cash floor, bounced cheque) once the push sender lands.
*Rationale:* nothing here needs a new entity; the stock-loss, discount, PPV and till reports are close to free against the shipped schema; the trust score is what makes every later number defensible; and the EFD list is the cheapest compliance win in the programme — the status column, the device serial, the error detail and the index all already exist.

**Wave 2 — the money reports.** Branch league table (with the "Unallocated" row and an honest branch-cost coverage flag) · Winners & losers with ABC and the four quadrants · Stock health (dead / slow / short / expiring / transfer opportunity) · My Real Profit in owner order with the bridge (and the 5190/5191 band decision resolved first) · Working capital days with the TZS translation · Supplier scorecard and price-jump detection · Factory yield and cost variance · Customer profitability and churn · Company/cost-centre budget vs actual with run-rate · Tax and compliance health (VAT + the existing WHT register) · Staff cost and productivity · Who Changed What · FX exposure off the four dedicated FX accounts.
*Rationale:* highest TZS recovered per hour of build. This is the wave the owner describes to other business owners as "the thing that showed me where the money was going." Most of it depends on the fact table, which is why the approval decision belongs at the start of wave 1.

**Wave 3 — gated on decisions, not on effort.** Cash forecast (after the commitment calendar) · Covenants, gearing and net debt (after the facility master and account tags) · Targets by branch **and** by agent/route/category (after the target table and the budget-uniqueness decision) · True consolidation (after the org-scoped read path, intercompany tag, translation and group COA) · Product-family hierarchy · Route call plans · EBITDA and adjusted EBITDA.
*Rationale:* every item here is blocked on an owner decision about what to capture, not on engineering capacity. Present them as decisions, one at a time, and build them as they are answered.
