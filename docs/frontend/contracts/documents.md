# API Contract — documents module (Phase-B frontend)

**Nav group:** Documents & PDF  
**Permission codes (use VERBATIM — do not invent):** DOCUMENT.RENDER, DOCUMENT.VIEW, DOCUMENT.TEMPLATE.MANAGE, DOCUMENT.BRANDING.MANAGE

## Module notes
PAGINATION: Only `GET /api/v1/documents` (the generated-documents render log) is paginated â€” it takes a Spring `Pageable` (page/size/sort query params) plus mandatory `companyId` (Long, required) and optional filters `type` (DocumentType enum), `sourceUid` (String), `from`/`to` (Instant, ISO-8601 date-time). It returns the platform envelope ApiResponse<List<GeneratedDocumentDto>> with a PageMeta (PageMeta.from(page)). `GET /api/v1/documents/templates` (returns a plain List, NOT paginated, NOT wrapped â€” returns raw List<DocumentTemplateDto>; it implicitly scopes to the caller's active company from RequestContext, NO query params). Branding GET/PUT return a single DocumentBrandingDto (not wrapped, not paginated).

ENVELOPE INCONSISTENCY (important for FE parsing): endpoints are NOT uniform. `GET /api/v1/documents` returns ApiResponse<List<GeneratedDocumentDto>> (wrapped + PageMeta). But `POST /api/v1/documents/render`, `GET /api/v1/documents/{uid}`, `GET /api/v1/documents/templates`, `PUT /api/v1/documents/templates/{uid}`, `GET /api/v1/documents/branding`, and `PUT /api/v1/documents/branding` all return the bare DTO/List from the controller method (the ADR claims an ApiResponseAdvice wraps these â€” assume the standard ApiResponse<T> envelope at runtime, but the controller return types are the raw DTOs). The two byte-stream endpoints (`GET /{uid}/download`, `GET /render`) return ResponseEntity<byte[]> with Content-Type application/pdf and Content-Disposition: attachment; filename="<type>-<documentNumber>.pdf" â€” these are NOT JSON; FE must treat them as binary/blob downloads.

PATH PREFIX: All paths are under /api/v1/documents (NOT /api/documents â€” the ADR-0023 prose tables omit the /v1, but the actual @RequestMapping bases are /api/v1/documents, /api/v1/documents/templates, /api/v1/documents/branding). Use /api/v1/documents.

LIFECYCLE / KEY ACTIONS (render service is read-only on source â€” NO GL/stock/financial mutation; ADR-0023 D-4/D-6): The core action is RENDER (POST /render or GET /render convenience-stream). Render orchestration: (1) resolve the (companyId, documentType) registry row â€” REFUSED if missing or status != ACTIVE ("document type not enabled", FR-DOC-03/BR-DOC-04); (2) resolve + scope-check the SOURCE company via the source module's findCompanyIdByUid; (3) load source DTO and enforce the per-type RENDERABLE-STATE rule (BR-DOC-05): INVOICE renderable only when source status FINALISED or VOID (REFUSED on DRAFT â€” "invoice not finalised"); PURCHASE_ORDER renderable when ORDERED+ or VOID (REFUSED on DRAFT); GOODS_RECEIPT renderable when RECEIVED or VOID (REFUSED on DRAFT); DELIVERY_NOTE renderable when CONFIRMED (v1 deliveries created CONFIRMED so always renderable); CREDIT_NOTE renderable in any posted state; AR_STATEMENT parameterised (always renderable for a valid customer+range). A VOID source still renders but stamped with a "VOID" watermark. On success it appends a generated_documents log row (append-only â€” never updated/deleted), emits DOCUMENT.GENERATED to the transactional outbox, and audits DOCUMENT.RENDER. DOWNLOAD re-renders bytes from the recorded source on each call (does NOT persist bytes, does NOT append a new log row by default â€” OQ-DOC-03), so a download reflects current source truth; content_hash detects divergence. TEMPLATE registry actions: only an UPDATE (PUT /templates/{uid}) to toggle MasterStatus ACTIVE/INACTIVE/ARCHIVED, set title, and set brandingId â€” there is NO create/delete (rows are seeded per-company by DocumentBrandingSeeder/V24 backfill for the six v1 types). BRANDING is a per-company singleton â€” GET (read) + PUT (upsert/update) only, NO create/delete; PUT does scopeGuard.assertCanActIn on the active company. UpdateDocumentTemplateRequest and UpdateDocumentBrandingRequest both carry an optimistic-lock `version` (Long) the FE must round-trip.

RENDER REQUEST SHAPE (RenderDocumentRequest): { documentType, sourceUid, sourceParams }. Provide sourceUid for the single-document types (INVOICE, PURCHASE_ORDER, GOODS_RECEIPT, DELIVERY_NOTE, CREDIT_NOTE); provide sourceParams (a JSON STRING, e.g. {"customerUid":..,"fromDate":..,"toDate":..}) for the parameterised AR_STATEMENT. The GET /render convenience form takes ?type=<DocumentType>&source=<uid>&params=<json-string> instead.

MONEY/CURRENCY: NONE of the documents-module wire DTOs carry money/currency fields â€” GeneratedDocumentDto has only byteSize (Integer) and no amount fields; branding has bankDetails (free text). Monetary content lives inside the rendered PDF bytes (copied verbatim from the source invoice/PO DTOs, base currency TZS), not in any JSON response. So the FE never parses money from this module's JSON.

REPORT/DOWNLOAD OUTPUT SHAPE: The "report" outputs here are PDF byte streams (application/pdf, attachment disposition, filename "<documenttype-lowercase>-<DOC-#### number>.pdf"). Two endpoints emit them: GET /{uid}/download and GET /render. v1 is PDF-only for transactional docs (statements upstream also support XLSX/CSV but documents endpoints emit PDF). FE should fetch these as blobs and trigger a browser download, not render inline JSON.

CHILD / NESTED RESOURCES: documents/templates and documents/branding are admin sub-resources nested under the documents base path but are distinct top-level UI screens (separate controllers). They are NOT children of a generated-document â€” they are company-level config. generated_documents reference a source document by sourceType+sourceUid (a cross-module pointer to Sales/Purchases/AR aggregates) but documents owns no nested collection endpoints. branding is a 1:1 per-company singleton (no list, no id-addressed CRUD). templates is a fixed-cardinality per-company list (one row per DocumentType, no create/delete via API).

ENUMS: DocumentType = INVOICE, AR_STATEMENT, PURCHASE_ORDER, GOODS_RECEIPT, DELIVERY_NOTE, CREDIT_NOTE (v1 renderable) + PAYSLIP, QUOTATION, DEBIT_NOTE (reserved, NOT rendered in v1 â€” render will fail for these). RendererKey = TRANSACTIONAL_PDF, STATEMENT_PDF. MasterStatus (template status) = ACTIVE, INACTIVE, ARCHIVED.

SCOPE/PERM NOTES: download uses @perm.scoped(#uid, 'generateddocument', 'DOCUMENT.RENDER'); GET /{uid} log read uses @perm.scoped(#uid, 'generateddocument', 'DOCUMENT.VIEW'); template update uses @perm.scoped(#uid, 'documenttemplate', 'DOCUMENT.TEMPLATE.MANAGE'). The two collection/render endpoints use @perm.has(...). Branding endpoints use @perm.has('DOCUMENT.BRANDING.MANAGE') (no scoped check; PUT adds a programmatic scopeGuard.assertCanActIn). All four permission codes are granted to ORG_ADMIN by default seed.
